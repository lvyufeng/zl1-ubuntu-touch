# 32 — 判别依据：容器走到 netd 之前，链路就是好的

**日期**: 2026-09-18
**结论**: 卡不卡，与**Android 容器走到了哪一步**相关——走到 netd 就卡，停在 zygote 之前就不卡。
**同时推翻了** [`27`](27-what-a-reachable-window-shows.md) §3 的"这是时刻表、不是概率"。

---

## 1. 现场

设备在 03:56:54 开机（同一张已知可用的 v63 镜像），到 04:33 已经 **uptime 2281 秒（38 分钟）**：

```
连续探测 60 秒：      可达 20 / 20
设备端 monitor 日志：  rndis0  RX 346876 包 / TX 406578 字节，收发包数都是 4265，同步增长
host usb0 MAC：        9e:a8:17:12:2a:76 —— 全程未变，没有任何重新枚举
```

RX 和 TX 都在涨、包数相等——**这是一条健康的双向链路，而且已经健康了 38 分钟。**

## 2. 但这次开机的容器**根本没起来**

把这次（健康）和 15:57 那次（卡死）的状态页逐项对比，差别非常集中：

| 关键字（在页面里出现次数） | 健康（04:33，uptime 2281s） | 卡死（15:57） |
| --- | ---: | ---: |
| `lxc-start` | 727 | 164 |
| `ueventd` | 11 | 20 |
| `qseecomd` | 2 | 4 |
| `hwservicemanager` | 3 | 4 |
| `servicemanager` | 3 | 4 |
| `vndservicemanager` | **0** | 2 |
| **`zygote`** | **0** | **57** |
| **`netd`** | **1** | **62** |
| **`fwmarkd`** | **0** | **2** |

**区别不是"容器起没起"，而是"容器走到了哪一步"。**

健康这次的容器卡在 zygote 之前——Android 框架从来没起来（`zygote` 一次都没有），
日志里也从没出现过 `init: Created socket '/dev/socket/fwmarkd'`。
而卡死的那次，`zygote`、`netd`、`vndservicemanager`、`fwmarkd` 全都在。

也就是说：

> **容器停在早期 → 链路一直是好的；容器走到 Android 网络栈（netd/fwmarkd）→ 链路在 ~50 秒断掉。**

[`30`](30-outbound-drops-before-the-queue.md) 里指向 netd 的那条推断**没有被推翻，而是被这次数据加强了**——
只是我之前把"容器在跑"当成了"netd 在跑"，这次才分清。

## 3. 但这意味着现在**两种状态不能同时成立**

这次链路好，代价是 **Android 根本没起来**。所以它不是一个可用的配置，
而是一个"Android 早早挂掉"的降级状态。

这才是真正的问题所在：**把 Android 推得越远，链路越容易死。**
移植要成功，必须让两者同时成立——所以不能靠"让容器起不来"来换链路。

## 4. 这推翻了什么

| 之前的说法 | 现在 |
| --- | --- |
| "每次开机头 ~50 秒通，之后必卡"（[`27`](27-what-a-reachable-window-shows.md)） | **不成立**。这次 38 分钟没卡 |
| "不是概率，是时刻表"（[`27`](27-what-a-reachable-window-shows.md) §3） | **反过来了**：它确实逐次开机不同。我当时只用了一次测量就下定义 |
| "容器/netd 起来就把链路打死"（[`30`](30-outbound-drops-before-the-queue.md)） | **没有被削弱，反而更准了**（见 §2）：不是"容器起来"，是"容器走到 netd" |

被推翻的只有"必然卡"这一条。而它的替身——"1/4 概率"——也不对：
现在有一个**候选判别依据**（容器走到哪一步），只是还需要更多样本确认。

我犯的错是同一个：**用一次测量去定义一个规律**。9 月 17 日看到几次卡死就说是"1/4 概率"，
同一天看到一次 50 秒的窗口就说是"时刻表"，今天又看到一次 38 分钟不卡。
三次都是从单个样本外推。

## 5. 顺带查清的一件事：SSH 不通的原因不是我的修复

这个 boot 里 8080/8081 在监听，**22 不在**。而 15:57 那次抓到的页面里 22 在监听。

rootfs 里有一个服务：

```
/etc/systemd/system/multi-user.target.wants/lxc-android-config-disable-ssh-socket.service
  -> /usr/lib/systemd/system/lxc-android-config-disable-ssh-socket.service
```

**Ubuntu Touch 自己会故意把 SSH socket 关掉**（名字很直白）。所以
[`scripts/fix-ssh-authorized-keys.sh`](../../scripts/fix-ssh-authorized-keys.sh) 把公钥和
`AuthorizedKeysFile` 都摆对了，只要这个服务还在跑，sshd 就不会监听。

也就是说：**SSH 那一步还缺一块——要 mask 掉这个服务**。这是可以提前做完的，不需要设备。

## 6. 现在在做什么

设备可达、稳定，所以挂了一个 **45 分钟长测**（`measure-link-stability.sh 45`）。
目的很直接：**看它会不会自己卡，以及卡在哪一秒**。

- 如果 45 分钟都不卡 → 这个 boot 是"好"的一类，需要用别的手段找判别依据
- 如果中途卡了 → 卡的时间点和当时的 `ip rule` / iptables 就能对上（不过这次没装 netsnap，
  所以只能记时间点，不能记现场）

无论哪种结果，都比继续猜有用。

## 7. 一个有价值的巧合

设备这次是在**断电/充电两个多小时后冷启动**的（01:35 掉线，03:56 重新出现）。
而之前卡死的几次，都是**紧接着上一次开机、由脚本连续重启**的。

我不能从两个样本下结论，但"连续重启 vs 冷启动"是一个**可以主动控制的变量**，
而且如果它成立，解释会很自然：连续重启时上一次的某些残留（userdata 里的状态、或
USB 设备侧的时序）会影响这一次。这值得作为下一个实验，而不是当作结论。

## 8. 当前的判断

| | |
| --- | --- |
| 已确认（[`30`](30-outbound-drops-before-the-queue.md)） | 卡死时出方向的包在设备队列**之前**被丢掉——所有 netdev 计数器都不动 |
| 已确认（本文 §2） | 链路是好的那几次开机，容器都停在 zygote/netd 之前；卡死的那几次，`zygote`/`netd`/`fwmarkd` 都在 |
| **候选判别依据** | **容器走到 Android 网络栈 → 链路断；没走到 → 链路好** |
| 根本矛盾（本文 §3） | 现在"链路好"和"Android 起得来"**不能同时成立**。这才是要解决的问题 |
| 下一步 | 45 分钟长测看它会不会晚卡；然后把 netsnap 装上去抓断点两侧的 `ip rule` / iptables，验证 netd 那条路 |
| 可以提前做 | mask 掉 `lxc-android-config-disable-ssh-socket.service`（已改进脚本），把 SSH 补完整 |

**不要用"让容器起不来"来换链路。** 那不是移植成功，那是移植没跑起来。
