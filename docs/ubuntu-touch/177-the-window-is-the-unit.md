# 177 — 窗口就是单位：温度是**均值**，而每个 `/s` 的除数**不是被问的那个秒数**

**日期**: 2026-09-26
**状态**: **改了仪器，并且又在设备上跑了四次**（同一趟启动，`2fbf9f8e-…`）。这一篇是
[`176`](176-six-runs-four-prices.md) 直接点名的下一步：把温度读数从**一个瞬间**改成**一个窗口的均值**，
然后**用同一个设计重跑**。两半是同一件事——**窗口是单位**——第一半让温度这一侧承认它（一个窗口没有
单一温度），第二半让 CPU 那一侧承认它（一个速率的分母必须是**这个窗口**的长度，不是**要求的**长度）。

**接续**: [`176`](176-six-runs-four-prices.md)（六次运行四个价钱，以及那个被量出来的 1.7 °C 偏差）、
[`175`](175-the-alternating-pair-is-the-second-design.md)（被重跑的那个设计）、
[`174`](174-the-two-units-are-one-mistake.md)（"一个数用一种单位，去比另一把另一种单位的尺"——这一页
是**同一个形状的第三次出现**，而且这一次在**仪器自己**里面）。

## 1. 一句话结论

| 问题 | 答案 |
|---|---|
| 这一轮买到了什么？ | **一个比值，和一个比值。**温度那一侧：`== thermal zones:` 现在是窗口内的**均值**，随样本数、走过的秒数、以及**动得最凶的那条 zone 自己的摆幅**一起印出来（docs 176 说"一个 zone 在 48 s 里走 3–4 °C"，现在这件事**自己会说话**）。CPU 那一侧：每个 `/s` 的除数改成**这个窗口量到的秒数**。 |
| 第二半为什么是错的？ | 因为**被除数和除数不是同一个窗口**。分子是两个 `/proc/stat` 快照之差，而这两个快照之间夹着 zone 采样循环**和两趟 `/proc` 进程遍历**——它们都在窗口**里面**；分母却是命令行上写的 `--seconds 10`。设备上量出来：`--seconds 10` 的两次 `/proc/stat` 相隔 **20.7 s**，所以**印出来的每一个速率都大了 2.07 倍**。 |
| 有多大？ | 设备实测（621 个进程、38 条 zone）：一趟 zone 遍历 **0.30 s**、一趟 `/proc` 遍历 **4.58 s**、`--seconds 10` 端到端 **23.8 s**。也就是说这台手机上"窗口"这个词从来不等于"被问的秒数"，而仪器一直按后者除。 |
| 温度那一侧修完是什么样？ | `take_window` 每**秒**走一遍 zone（38 条 = 76 次 fork ≈ 0.30 s），把**一次采样自己的代价从它自己的睡眠里减掉**（`sleep 1` 曾经**叠在**采样之上，于是 30 s 的窗口是 42 s），`thermal_summary` 报**均值**并印出样本数、走过的秒数、最宽的摆幅。一次 10 s 窗口的实机输出：`mean of 10 sample(s) walked over 10s of this window; the widest zone moved 9.0 C -- thermal_zone11; 24 zone(s) moved 0.2 C or more across it`。 |
| `/s` 修完是什么样？ | `(<ticks> ticks, <X> s measured)`——**X 是量出来的**，每个窗口**各用各的**（`--ab` 的两个窗口因此各除各的）。时钟读不到时它印 `REQUESTED -- the clock did not advance` 并把回落写到 stderr，**不除零、也不假装那是测量**。 |
| 六次运行的四个价钱，现在重跑成什么样？ | 见 §7：**同一个设计、同一台手机、同一趟启动**，四次运行的读数落在 **2.10–2.73 °C**、误差棒 0.10–0.18（旧读数 0.38–0.97），四次都是 `COST-MEASURED`。 |
| 离线怎么被证明的？ | harness **59 → 76 条全绿**：新开一节（3c），一个**会走的时钟**（fixture 的 `/proc/uptime` 过去**一动不动**——所以"回落到被问的秒数"是唯一被跑过的分支）、450 个假进程 + 400 条假 zone（没有这两样，"量到的"和"要求的"是同一个数，这条断言**分不出两种行为**）、**四条**来自同一次运行的断言、**三个**变异（都先证明**落进了被测副本**）。 |
| 设备现在怎么样？ | **在跑**（`33e80afe`，`18d1:d001`，RNDIS），`boot_id 2fbf9f8e-deea-4955-ad0c-6bddf0fb14f5`——**和 docs 176 那六次是同一趟启动**。这一轮只读；唯一被写的是 governor，而每一次运行都用自己的 EXIT trap 把四个核放回 `interactive` 并读回复核。 |

## 2. 两半是同一件事

`zl1-thermal.sh` 的头部有一句从 docs 72 起就在的话：**"这里的每一个 CPU 数字都是一个窗口上的差，
别的一概不是"**。这句话对 CPU 侧成立（`/proc/stat` 两次快照，差就是差），而它**对温度侧从来没有成立过**：
zone 表是在窗口**睡完之后**读的**一次**。于是同一个文件里有两个时间观：

| | CPU 侧 | 温度侧（到 docs 177 为止） |
|---|---|---|
| 怎么读 | 两次快照，取差 | 一次快照 |
| 一个窗口里发生什么 | 差值累积 | 什么都没发生——读的是一个**瞬间** |
| 代表什么 | 窗口 | 窗口**最后一刻** |

docs 176 量到的是这个不一致的代价：同一次运行、同一个配对，**快照 +2.30、窗口均值 +0.61**，差 1.7 °C，
而效应本身约 2.3 °C——**四分之三**。

修完温度侧之后，同一个文件里还剩**第二处**同样的不一致，而且它在 CPU 侧的另一端：**分母**。
CPU 侧的分子是一个**窗口**（两次快照之间的一切），分母却是**要求**（命令行参数）。

```
        |<------------------- 窗口（两次 /proc/stat 快照之间）------------------->|
        |  snap_procs A  |    zone 循环 (SECONDS_WIN)    |  snap_procs B  |
                            ^                                             ^
                            |                                             |
                       /proc/stat a                                  /proc/stat b
                            |                                             |
                     分母曾是 SECONDS_WIN ← 只有这一段，而分子是全部
```

设备上：`snap_procs` 4.58 s × 2 + zone 循环 10 s ≈ **20.7 s**，除以 **10**。

## 3. 第二半：设备上量出来的数

2026-09-26、`boot_id 2fbf9f8e`、621 个进程、38 条 thermal zone：

| 量什么 | 值 | 怎么量的 |
|---|---|---|
| 一趟 zone 遍历（38 条，`cat type` + `cat temp`） | **0.30 s** | `cut -d' ' -f1 /proc/uptime` 前后夹一次 |
| 一趟 `/proc` 进程遍历（621 个） | **4.58 s** | 同上 |
| `--seconds 10` **端到端** | **23.8 s** | 同上（旧版同一条命令是 28.1 s） |
| 两次 `/proc/stat` 相隔 | **20.7 s** | 修完之后仪器自己印出来的 `measured` |

所以：旧版每一个 `/s` 都是真值的 **20.7 / 10 = 2.07 倍**。而且这**不是过时数据造成的**——
0.30 s 和 4.58 s 是**这一轮**在**同一台手机**上量的，`20.7 s` 是**修完之后的仪器自己报的**。

三处修改：

* **采样循环把一次采样的代价从它自己的睡眠里减掉**。`sleep 1` 曾经叠在 0.30 s 的遍历之上，
  于是"30 s 的窗口"是 1.3–1.4 倍的 30 s。现在每一次迭代量自己花了多久，只睡剩下的（下界 0.05 s，
  所以遍历比一秒还慢时循环仍然结束——**循环的上界是次数，不是时钟**）。
* **除数改成这个窗口自己量到的秒数**（`/proc/uptime` 的小数秒——这块板子的 RTC 读 1970，
  是这里**唯一**会走的钟），**按窗口存**（`$TMP/wsecs.<label>`），因为 `--ab` 会把窗口 A 的表
  **打印在窗口 B 已经取完之后**——一个全局变量会让 A 的 tick 数除以 B 的秒数。
* **读不到时说出来**：印 `REQUESTED -- the clock did not advance`，把回落写到 stderr，
  并且**照常打印速率**——一个不走的钟不能变成一次除零，也不能被当成一次测量。

## 4. 第一半：温度是窗口内的均值

（这一半在 docs 176 的结尾就点过名，这里是它的落地。）

* `zone_raw` = 一次**瞬间**读数（原来 `zone_read` 的全部内容）；`zone_read` 现在只是它的一个包装，
  而**窗口里的任何东西都不再调用 `zone_read`**——注释里写明了这一句，harness 也静态钉住了它。
* `take_window` 在窗口里**每秒**把 38 条 zone 追加进 `$TMP/zones.samples.<label>`。
* `zone_mean` 按 **(name, type)** 对**原始值**求平均，**再**过一次单位表，输出形状和 `zone_read` 逐字节同构
  ——所以 `hottest:`、单位标志、以及**两个解析 `$4 == "C"` 的 A/B 仪器**都不用改。
* `zone_spread` **先缩放再相减**（原始单位因驱动而异，直接相减是拿 deci-degC 比 milli-degC），
  印 `name 摆幅 样本数`；总结行把**最宽的那条**和"移动 ≥0.2 °C 的 zone 数"一起印出来，
  因为**一条 zone 自己的摆幅接近要量的差时，那个数就不是一个安静的数**（docs 176：`thermal_zone12`
  在**空载**下 4 秒走过 412 → 480 → 406）。

一次 10 s 窗口的实机读数（2026-09-26，同一趟启动）：

```
   hottest: tsens_tz_sensor8 44.5 C  (raw 444 = deci-degC, of 38 zones; 10 flagged above)
   (mean of 10 sample(s) walked over 10s of this window; the widest zone moved 9.0 C -- thermal_zone11;
    24 zone(s) moved 0.2 C or more across it)
```

**"走过的 10s"** 本身就说明第一半和第二半是同一件事：窗口的**长度**现在是**量出来的**，
而且它等于被问的那个数——因为采样不再把自己加在窗口上。

## 5. 离线怎么被证明的：76 条，四个断言，三个变异

新开的 3c 节有一个前提：**没有会走的时钟、没有值得遍历的进程表，这条断言分不出两种行为**。
fixture 的 `/proc/uptime` 过去**整场一动不动**，所以每个窗口都量到 0.00 s、都回落到"要求的长度"——
**回落是唯一被跑过的分支**。现在 fixture 有一个写 `/proc/uptime` 和 `/proc/stat` 的 ticker
（`.new` + `mv`：撕裂读会给仪器一个 9892 秒的窗口），加上 450 个假进程和 400 条假 zone。

一次运行（要求 3 s）给出四条断言：

| 断言 | 实测 |
|---|---|
| 印出来的是**量到的**、带小数、而且**长于**要求的 3 s | `5.7 s`——两趟 `/proc` 遍历在窗口**里面** |
| 而**采样自己走过的**是要求的 3 s（代价从睡眠里减掉了） | `walked over 3s` |
| 打印的速率复现的是**那些 tick 除以量到的秒数** | `r × 5.7 ≈ ticks`，误差 <1% |
| 而**要求的 3 s 复现不出它** | `r × 3 = 0.68 × ticks` |
| 一个**停住的钟**：印 `REQUESTED`、把回落写进 stderr、**照常打印速率**、退出 0 | 四条各自断言 |

三个变异（都**先证明落进了被测副本**，再跑）：

| 变异 | 把什么放回去 | 它必须被看见 |
|---|---|---|
| `th.req.sh` | 两个调用点恢复成 `$SECONDS_WIN`（**就是修之前的那两行**） | 速率断言红**并且**印出来的秒数也变回请求值——`verdict` 打印的是它自己除的那个变量，所以这里**只能有一个变异**，两个"各管一半"的变异在这份源码里不存在 |
| `th.nosleep.sh` | `sleep "$zl1_rest"` → `sleep 1` | 采样走过的秒数从 **3 s 涨到 5 s**（400 条假 zone 就是为此存在的：一条 zone 太便宜时，两种行为给出同一个整数） |

（第三处 fixture 修补是**均值那一节自己**：`mean_scenario` 现在也开着钟，于是 `walked over 6s`
是一个真读数，而不再是一个 `0`。）

## 6. 那个"要求的秒数"曾经让 `--status` 说谎

`zl1-governor-temp-ab.sh` 的 `--status` 一直承诺"每个窗口 = 它的长度 **+ 大约 13 s** 走 `/proc`"。
**修之前这不是真的**：窗口是 `1.4 × 长度 + 13`（采样把自己加了上去），所以 `--seconds 30` 的实际墙钟
比承诺的长约 25%。docs 177 之后 `长度 + 13` **就是**真的（设备实测：10 s 窗口 → 23.8 s），
于是这一轮把那句话改成带**重新测量**的引用（13.8 s / 23.8 s）。仪器上跑的仍然是安装时的那一份
（md5 `a148b614…`），与仓库的差异**只有三处注释和一行 `say` 文本**，没有一行代码——`diff` 的输出在
证据日志里。

## 7. 设备上的读数：同一个设计，四次

同一趟启动（`2fbf9f8e-…`，**和 docs 176 那六次是同一趟**）、同一台手机、同一个设计（4 对、30 s 窗口、
5 s settle、**并排交替**），把**两次修好之后的仪器**放进去，跑了四次（证据日志
`evidence/governor-temp-ab-2026-09-26-window-mean-four-runs.log`，四次运行的完整输出都在里面）：

| 次 | 预注册的主 zone | 读数 | se | 两倍标准误区间 | 判词 |
|---|---|---|---|---|---|
| 1 | `thermal_zone12` (`tsens_tz_sensor11`) | **+2.65 °C** | 0.10 | [2.45, 2.85] | `COST-MEASURED` |
| 2 | `thermal_zone9` (`tsens_tz_sensor8`) | **+2.20 °C** | 0.12 | [1.96, 2.44] | `COST-MEASURED` |
| 3 | `thermal_zone12` (`tsens_tz_sensor11`) | **+2.73 °C** | 0.14 | [2.45, 3.01] | `COST-MEASURED` |
| 4 | `thermal_zone9` (`tsens_tz_sensor8`) | **+2.10 °C** | 0.18 | [1.74, 2.46] | `COST-MEASURED` |

**四次读数落在 2.10–2.73 °C**，四个区间**下界都在 0.2 °C 之上**，没有一个区间**跨过**门槛。
对照 docs 176 同一趟启动、同一个设计、旧读数给出的六次：

```
旧读数（末瞬间）:  +2.03 (se 0.38)   -0.58   +2.48   +5.88 (se 0.97)   +2.27   +2.30 °C
新读数（窗口均值）: +2.65 (se 0.10)   +2.20   +2.73   +2.10 (se 0.18)
```

两组的差别**只有读数**，而这件事在那一次是被**量出来的**：第 6 次运行里并排跑的按名字采样器，
在**同一个窗口**上给出 +0.61，而快照给 +2.30。

三件值得单独说的事：

* **误差棒小了三倍**（0.10–0.18 对 0.38–0.97），而**符号没变**：两组里凡是**读数**（而不是 artifact）
  的都为正。均值拿走的是"挑哪个瞬间"这个**系统性**部分，不是效应本身。
* **主 zone 仍然换手**（zone12 / zone9 各两次），因为它是 **A.1 里最热的那个传感器**。
  但**读数几乎不再依赖它**：第 1 次运行里 **21 条 tsens zone 全部为正，+0.75 到 +2.65**——
  zone 之间的散布现在是**效应的形状**，不是噪声围着一个数。
* **控制线**说这台手机在每次运行期间**自己**在以 0.11–0.22 °C/窗口 移动，**balance** 说两半的平均位置
  是 4.50 和 4.50（失衡 0.00）——交替顺序在**干活**，不是装饰。
* **两半的 busy 不一样**（fix 约 1.21–1.28 核、pinned 约 0.74–0.76 核，四个核里）。这是
  `performance` 在这台手机上的**性质**，仪器**印出来**而不是去修正它；它也是判词里
  "这是**一个读数**、不是一个普适的价格"那半句的理由。

**②的价钱仍然不是一个定值**——四次给的是一个**窄区间**（2.1–2.7 °C，主 zone 上的两倍标准误 ±0.2），
而且**四次都在同一趟启动里**、负载/环境/充电状态都没控制。

## 8. 这一页**没有**成立的东西

* **②的价钱仍然没有"一个数"。** 这一轮给的是一个**更窄的区间**，不是一个定值；
  而"这个数能不能在两次运行之间重复"是这一轮唯一能回答的那个问题（§7）。
* **热时间常数仍然没量过。** 窗口和那个常数同量级时，这个设计**低估**效应（偏在"看起来更便宜"那一侧）。
* **`performance` 的余热、窗口之间的 settle 是否够长、切换 governor 本身是否引入扰动**——三件都没量过。
* **温度那一侧仍然是一秒一个样本**：比"一个瞬间"好，但不是连续记录。9.0 °C 的摆幅说明**秒级噪声是真实存在的**，
  而均值只是把它的**均值**拿走，没有把它**消掉**。
* **`--ab` 的 A/B 比较现在是均值对均值**，但**没有任何人在设备上跑过 `--ab`** 来确认这一点
  （heat chain 会在下一次跑的时候遇到它）。
* **`REQUESTED` 那条分支在设备上没有被触发过**（这台手机的 `/proc/uptime` 一直在走），
  它只在离线 fixture 里被跑过。
* **跨重启的持久性仍然没量过。**
* **设备时钟仍然是错的**（读 1970），这一页没有碰它。
