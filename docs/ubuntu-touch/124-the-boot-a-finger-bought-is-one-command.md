## 1. 一句话结论

| 问题 | 答案 |
|---|---|
| 这一轮做了什么？ | 把 doc 122 §9 那张**手打的命令清单**做成了一条命令，而且**顺序是被强制的**，不是被记住的 |
| 为什么需要它？ | 从 EDL 出来要**物理长按电源 10–20 秒**，脚本帮不上忙。所以那之后的 boot 是**用一根手指买来的资源**，而浪费它的方式就是"五六条手打命令，做一半然后放弃"——**这正是 heat chain 当年为它自己写的理由，只是高了一层** |
| 顺序为什么是被强制的？ | 因为每一步的下游都有一步**拒绝**在前面：01 必须最先，因为 03 会杀掉 01 要读的 keeper 的 pid 和 ticks；02 和 03 必须早于 05，因为它们各自武装 05 的一道门 |
| 它比手打多做什么？ | **每一步做完之后，从设备上重读下一步的前置条件**：02 之后读 `download_mode`，03 之后读 keeper 是否还在。在 05 才发现 A 或 C 根本没动，是在**唯一那个 boot 的末尾**才发现的 |
| `--apply-trial` 是什么？ | **一个单独的开关。**它把第 05 步从 `--status` 升级成那次**写入**（写 SoC 的电源参数）。`--yes` **不**蕴含它，而且**除非 02 在同一次调用里真的跑了，它会被拒绝** |
| 离线验证？ | `zl1-one-boot-runbook-selftest.sh` **90 检查 / 0 失败**；四个 callee 是**会记录调用的替身**（各自有自己的 harness），另外它自己的被测对象还断言"声明的步骤表和实际执行顺序一致" |
| 家族全量跑呢？ | **18 个 harness / 1967 检查 / 全绿** |
| 动设备了吗？ | **没有。**这条命令**从来没有在设备上跑过**；设备仍在 EDL |

## 2. 顺序不是偏好，是被强制的

五步，每一步的位置都有一个**能核对**的理由：

| 步 | 做什么 | 为什么必须在这个位置 |
|---|---|---|
| **01 capture** | 只读：post-mortem 最先，然后是这个 boot 自己的读数（04b modem、04c sleep） | **必须最先**，因为它读的三件事**在这个同样的 boot 里会消失**：debug keeper 的 pid 和累计 CPU ticks（03 会杀掉它）、以及给那次猎杀发许可证的 netwatch 日志 |
| **02 panic guard** | `install-no-edl-on-panic.sh --install` | **在任何可能 panic 的事情之前**，而且它是这一串里**唯一跨 boot** 的一步：`--install` 写的 unit 每次 boot 都把 `download_mode` 清成 0，所以**装一次，之后每个 boot 都从"panic→EDL 已解除"开始**。它同时也武装**当前这个 boot**（`systemctl enable --now` 当场就跑 applier），而那正是第 05 步的门 A |
| **03 heat chain** | 前两个发烫修复 | **必须早于 05**，因为在这里退役 keeper 正是**武装实验的门 C** 的那件事——一个从不停下来的核不会进入深 idle，所以 keeper 在跑的时候实验会拒绝。这也是**唯一可能把会话弄掉**的一步（它的 activate 阶段会重新枚举 USB gadget 并等 90 秒让 netwatch 自愈），所以它不排在第一个：到那时**只存在于这个 boot 的东西已经落盘了** |
| **04 fingerprint** | 建那个缺失的目录 | **顺序无关**，放在这里是因为它只是一次小的 unit 安装加一次目录回读；它的判据是一条以后随时可以数的日志 |
| **05 trial** | 最后一个，**只读** | 它的拒绝要拿 02 和 03 **实际做了什么**来核对，所以这是整个 boot 里**第一次** A 和 C 可以同时成立。`--apply-trial` 才把它升级成写入 |

**这里有一个没人写下来过的推论**：doc 122 说实验的三道门是"拒绝"，但没说**那三道门是怎么被满足的**。
答案是：**门 A 由第 02 步满足，门 C 由第 03 步满足**，门 B（cpuidle 可读）只能读。
所以实验在序列里的位置不是"放最后比较方便"，而是**只有这个位置它才可能通过**。

## 3. 它比手打多出来的那一件事

doc 122 §9 那张清单是六条手打的命令。这一轮加的不是"把它们串起来"，是**每一步做完之后替下一步看一眼**：

```
02 之后   ->  从设备读 download_mode        A 满足了吗？没满足，原因在 02 或驱动，不在实验
03 之后   ->  从设备读 keeper 是否还在      C 满足了吗？没满足，原因在 03，不在实验
```

两条读数都是**设备上的读数**，不是步骤的退出码。一个 installer 退出 0 和一个旋钮真的动了，
是**两件不同的事实**，而把序列排好整个意义就在于：**最后一步依赖的是第二件**。

**而这个"读数不是退出码"的纪律当场抓到了两个缺陷**，而且形态一样：

* `download_mode` 的读数是 `<路径>=<值>`，**值在末尾**。第一版写的是 `case "$A_AFTER" in 0*)`——
  匹配值在**开头**。于是**不管设备怎么读，A 永远报"未满足"**：一条**任何场景都改不动**的检查。
  harness 把那个 flag 移来移去才发现（`--status` 里那一份是同一个错误写了两遍，被抓到第二次）。
* `run_bg` 的最后一条命令是一个**赋值**，而函数返回最后一条命令的状态——赋值永远是 0。
  于是 `rc=$?` 拿到的**永远是 0**，**实验自己的退出码（REFUTED / REFUSED / 写入失败）从来没有被报出来过**。
  harness 驱动 `FP_RC_TRIAL` 才发现。

## 4. 三条安全线

1. **`--yes` 不蕴含 `--apply-trial`。**`--yes` 授权的是**序列**，不是**对 SoC 电源参数的一次写入**。
   那一步是一件**决定**，而这次决定不该藏在一个"跑一遍"的开关后面。
2. **没有 02 就不许 apply。**而且判据是"**02 在这次调用里跑了**"，不是"02 没被 skip"——
   `--only 05-trial` 时 02 既没被 skip 也没跑，那是**同一个危险的另一种拼法**。
   这是本脚本唯一一条关于**它自己**的拒绝：一次 hang 在这里是一次 EDL，而 panic guard 正是把
   "hang 变成重启"的那件东西。
3. **计划表和执行顺序必须一致。**`STEPS` 是一张表，而顺序是下面那一串 `if wanted ...` 代码块——
   **两件独立的东西**。所以它们被**互相核对**：跑完之后，实际执行过的步骤列表必须等于按
   `--skip`/`--only` 过滤后的 `STEPS`，不等就**明说这是本脚本的缺陷，不是设备上的问题**。

   这一条是**被一次变异逼出来的**：把 `STEPS` 里两项对调，**零个失败**——
   因为它只改计划、不改执行，而当时没有任何东西检查两者是否一致。
   **一条任何场景都改不动的检查，不是检查。**

## 5. 离线验证：90 检查

`scripts/host/zl1-one-boot-runbook-selftest.sh`，**90 检查 / 0 失败**。
四个 callee 是**会记录调用的替身**（每个都有自己的 harness；这里要测的是**它们被调用了、顺序对、参数对**），
传输层和家族里其他 harness 一样：**stub 目录就是设备**，假根 + 沙箱 `PATH`。

它检查的：

| 节 | 什么 |
|---|---|
| 1 | **设备不在时一个 ssh/scp 都不发**（lsusb 那条**要**发——那正是判断 EDL 的问题），三种"不在"各自落在自己的读数上；serial 是**前缀**（等值判断会把一台在线的机器报成 absent） |
| 2 | `--status` **逐字节不写**（不是 grep 源码，是前后清单 + md5）；未知参数、**未知步骤名**都拒绝——`--skip 03-heatchain`（打错字）**不许**静默地把 03 跑掉 |
| 3 | 五步的**顺序**与**每一步的参数**；`--settle` 原样传到 heat chain（它的 90 秒默认值是 netwatch 需要的间隔，不许被悄悄缩短）；以及**计划表与执行顺序一致** |
| 4 | `--skip`/`--only` 的选择，以及被跳过的步骤**在 INDEX 里有它的行**（缺一行会被读成"它不在计划里"） |
| 5 | **两条读数跟着设备走**：fixture 把 `download_mode` 改成 0/1、把 keeper 放上/拿掉，同一句提示必须跟着变；链接在步骤之后断掉时，读数必须是 `UNREADABLE` **而不是一个值** |
| 6 | `--apply-trial` 的三种情形：skip 02 时拒绝、`--only 05` 时**同样**拒绝、02 跑过时第 05 步拿到 `--apply`；以及实验自己的 0/1/3 分别被读成"这是一次量"、"这是关于这次运行的陈述"、"这是一次拒绝" |
| 7 | 一步失败**不停下后面的步骤**，但退出码照样报出来 |
| 8 | 归档：INDEX.txt 的行、每步一个文件、`sha256sum -c` 通过 |
| 9 | 中断：**归档已跑的**、退出 3、而且**这份残缺的归档自己校验通过**（handler 往步骤文件里写字会让它失败——capture 记过这个） |
| 10–11 | `--help` 打的是自己的 header；退出码契约写在 header 里；以及**本 harness 在健康页里的引用不会漂移** |

**变异测试**（每一条都真的跑过）：把 `STEPS` 里两项对调 → 计划/执行不一致，红；
删掉 `APPLY_TRIAL` 的那道门 → 4 条红；把 C 的读数写死成 `none` → 3 条红。

## 6. 这一篇**不**证明什么

* **不证明这条命令在设备上能跑完。**它**从来没有在设备上跑过**。四个 callee 在真机上是**真的**
  安装器和真的链条，而在真机上它们会真的写、真的可能把会话弄掉、真的可能失败。
* **不证明顺序是"最优"的。**它证明的是**每一步的位置都有一个能核对的理由**，
  以及**顺序被执行顺序强制**（不一致就报错），不是证明没有别的顺序也能工作。
* **不证明 `--apply-trial` 安全。**它的安全性来自实验自己的三道门和"值不持久"，
  以及这里那条"没装 panic guard 就不许 apply"的拒绝——**都不来自任何一次真机运行**。
* **不证明"跑完这一条，发烫就解决了"。**它做的只是**把三个修复装上并读回**：
  前两个由 03 装，第三个是一次**要被推翻也可能的实验**（doc 122）。

## 7. 设备状态与下一步

整轮没有动设备：没有写任何分区或 boot，没有跑 QDL/QFIL，没有重启，没有绕过权限。
设备仍在 **Qualcomm EDL**（`05c6:9008`，`Bus 003 Device 020`，无序列号）。

```
# 0. 物理长按 POWER 10–20 秒，等 RNDIS 和 ssh
scripts/host/zl1-one-boot-runbook.sh --status     # 只读：这个 boot 上还剩什么没做
scripts/host/zl1-one-boot-runbook.sh --yes        # 五步，按唯一能成立的顺序
```

`--apply-trial` 是之后单独的一次决定。在那之前，这一篇里的一切仍然只是**离线可以核对**的东西。
