  and the part of mount_android_partitions that decides what happens when the glob matches nothing:
    2:	fstab=$1

  READ THAT AS THREE FACTS: the fstab argument is a GLOB; it is expanded unquoted; and the only
  consumer of it is 'cat ${fstab} | while read line'. A glob that matches no file makes cat exit
  non-zero AND PRINT NOTHING, so the loop body -- the mkdir and the mount -- never executes. There
  is no else-branch and no message: an empty fstab and a missing fstab are the same silence.

== 5. the verdict ==

== verdict: THE LOOP IS EMPTY
   The ramdisk halium extracts -- the one that lands ON the glob's directory -- carries
   65 entries and NOT ONE of them has 'fstab' in its name. So:

     'cat /var/lib/lxc/android/rootfs/fstab*'  ->  prints an error, exits non-zero
     the 'while read' body                    ->  NEVER RUNS
     the mkdir and the mount                  ->  never happen
     the stderr                              ->  goes to the initrd's console, and the boot continues

   Which is the mechanism docs 120 named as hypothesis (a) and left for the device: NOTHING IS
   MOUNTED, AND NOTHING IS REPORTED. The container's /vendor/firmware_mnt -- the empty directory the
   ramdisk carries for exactly this mount -- stays empty, so the modem firmware the kernel asks for
   is not there to be loaded, however correct the path in the cmdline is.

   What this is NOT: a claim about the phone. It is a claim about two IMAGE FILES, and the images are
   the ones this project staged and the one that was pushed to /data/system.img. The device-side
   confirmation is one command, and it is the one docs 120 already wrote into the probe:

     ls -l /var/lib/lxc/android/rootfs/ | grep -c fstab      # expect 0

   If that ever reads non-zero, the image on the phone is NOT the image this was read from, and that
   is the finding -- not a contradiction.

   THE REPAIRS, and neither is applied here because both are device side:
     (a) give the ramdisk an fstab -- a file inside /data/system.img, i.e. a USERDATA-side write, not
         a critical partition, but it means rewriting a 4 GB image the container boots from;
     (b) make the boot script not depend on that file -- an initrd change, i.e. a 'fastboot flash
         boot', which is what this project already does routinely and can roll back.
   Which one is right depends on which file the NEXT change wants to own, and that is a decision for
   a person with the device in hand.
