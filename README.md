# LeEco zl1 OS Porting Notes

This repository tracks research and experiments for alternate operating systems on the LeEco Pro3 (`zl1`, `le_zl1`, Qualcomm MSM8996 / Snapdragon 821).

## Active track: Ubuntu Touch / Halium 9

The current focus is rebuilding Ubuntu Touch / Halium 9 boot support for `zl1` after older community prebuilt artifacts disappeared.

Known starting point:

- Device: LeEco Pro3 (`le_zl1` / `zl1`)
- Android base observed on the connected device: Android 9, SDK 28
- Treble: enabled
- VNDK: 28
- Slot layout: A-only / no slot suffix observed
- Boot state: orange

The recommended first approach is to reproduce the historical community Halium 9 path using Android 9 / LineageOS 16-era sources and the `halium-leeco` `halium-9.0` branches.

- [`docs/ubuntu-touch/110-the-lshal-columns-have-a-definition.md`](docs/ubuntu-touch/110-the-lshal-columns-have-a-definition.md) — **the `lshal` columns do have a definition, and the recording already said the service is registered.** Docs 109 left one layer open: whether the GNSS HIDL service is registered, because "nothing in this tree records what `lshal`'s columns mean on this image". That was true of the *output* and false of the *source* — the image's own build tree carries `lshal` at `frameworks/native/cmds/lshal`, and `/mnt/android-sys-test/bin/lshal` is only a 68 KB shell whose real code is in `liblshal.so` (334 KB), which contains the literals verbatim (`Thread Use`, `are you root?`, `All binderized services (registered services through hwservicemanager)`) — so the source reading applies to this image, checked the way docs 102 demands. Three rules follow: lshal prints three tables separated by blank lines, each introduced by such a literal; the default columns are `{RELEASED, INTERFACE_NAME, THREADS, SERVER_PID, CLIENT_PIDS}`; and `hash` — which the `R` column reads — is assigned in exactly ONE place, `fetchBinderizedEntry()`, i.e. the FIRST table only. So a row in table 1 means hwservicemanager lists it (registered) and `R = Y` means it answered `interfaceChain()`/`getHashChain()` (live), and table 2's own description ("the Server / Server CMD column can be ignored") says which columns may only be read where. **Read that way, the 2026-09-23 recording says `android.hardware.gnss@1.0::IGnss/default` IS registered and live** — the answer was already in the archive. The probe now captures the listing whole (the old `grep gnss` ate the blank lines that separate the tables — the capture was lossy, not just unjudged), reads it, adds a `gnss-not-registered` rung, moves `no-gnss-listing` ABOVE `daemon-only` where it was nearly dead code (any boot that logged a provider line reported `daemon-only` even with no GNSS HAL at all), and prints its verdict's name on its own `VERDICT:` line. `zl1-gps-selftest.sh` is **129 checks** (was 99) with **nine mutations each failing** — and two of them first *did not*, which is recorded: an always-`Y` R column had nowhere to show up until a blank-`R` fixture was added, and the Server/Threads scenario used the recording's `257/257` that the table-2 row also carries, so the fixture's own expected value could be produced by the wrong implementation. It does not prove GPS works, and it does not prove who made the call.
- [`docs/ubuntu-touch/111-netwatch-over-ssh-and-the-twrp-step-that-bought-nothing.md`](docs/ubuntu-touch/111-netwatch-over-ssh-and-the-twrp-step-that-bought-nothing.md) — **the netwatch can be installed over ssh now, and the TWRP step was buying nothing.** The remaining heat fix is a chain: install the netwatch build that has `ensure_addrs()` → reboot → `zl1-boot-address-check.sh` reads `netwatch-configured` → only then is retiring the v63 debug keeper licensed. It is stuck at step one because the installed build has no `ensure_addrs()`, and `install-netwatch-service.sh` was the **only** unit installer in this port that needed TWRP — every other one (fingerprint, retire-keeper, container-desabotage, repowerd-ordering, shell-back-key) already writes `/etc/systemd/system` over ssh on a booted device, because that path IS the live bind mount of the same directory. So `--yes --ssh` was added, and three things had to be right. **The path follows the transport and getting it wrong is silent**: over adb/TWRP userdata is a plain `/data`, so it is `/data/system-data/etc/systemd/system`; over ssh that same name is the ANDROID CONTAINER's `/data`, so it is `/etc/systemd/system` — a write there lands in the container's own filesystem, looks like success, and is gone at the next boot (the same shape as the misc partition path differing between UT and TWRP). **It replaces the script of a RUNNING service, atomically**: `sh` reads a script from the file as it executes it, so `cat > $DEST` would truncate the file under the live watchdog and let it execute whatever arrived next — the payload goes to `$DEST.new`, is byte-counted and grepped back **from the device**, then `mv`d (rename(2)) into place, so the running shell keeps its descriptor on the old inode. Nothing is restarted, and it says so. **And the misc backup is required, not taken** — reading a raw partition over ssh would be a second implementation of the cross-checked read the adb path already does, so it refuses by name and names the route that takes one. `zl1-installers-selftest.sh` is **278 checks** (was 229) with **five mutations each failing** — pointing the ssh path at the TWRP tree gives 22 red, writing straight onto the live path gives 19. Not run on a device: it is in EDL.
- [`docs/ubuntu-touch/112-the-gate-is-a-race-and-it-ends-when-the-keeper-does.md`](docs/ubuntu-touch/112-the-gate-is-a-race-and-it-ends-when-the-keeper-does.md) — **the gate that licenses the second half of the heat fix is a race, and the race ends exactly when the answer stops being needed.** Docs 88/94 set it: retire the v63 debug keeper only after `zl1-boot-address-check.sh` reads `netwatch-configured`, which needs an `ADDRS:` line in the netwatch log. But `ensure_addrs()` logs **only when an address was missing**, and the keeper re-adds both addresses **every second** (`configure_iface rndis0` in the same 1 Hz loop body that raises the gadget) -- so on a keeper-alive boot the netwatch can produce that line only if one of its 2 s samples lands between an address going missing and the keeper's next tick. That window is somewhere between tens of milliseconds and a second wide (it depends on an unmeasured asynchronous gadget bind) and has never been measured, which makes **`inconclusive` the expected verdict on most boots** and "re-run the boot and look again" a **re-roll of a coin, each roll being a device boot**, not a retry. The asymmetry is the whole point: that window exists *only because the keeper is there*, and in the configuration the gate is actually asking about -- no keeper -- nothing else configures the interface, so the line is deterministic. So the check's `inconclusive` now comes in **two shapes that must not read the same** (keeper alive: it had nothing to do; keeper gone: something this script cannot see applied them), states the arithmetic, and points at a new **write-capable probe**, `scripts/device/zl1-address-owner-proof.sh --yes`: SIGSTOP the keeper (read back as `T`), take `192.168.2.15/24` off `rndis0` (read back as gone), require the netwatch to notice and restore it **and** to log a *new* line (anchored to the log offset taken first, so an older boot's line cannot count) -- then undo: resume the keeper and restore the address itself if the netwatch did not. `proof-unclear` exists because a restored address with no line is not proof. Three things are not configurable: the address is a literal (the SSH address is unreachable by any flag), the keeper **cannot stay stopped** (a detached `setsid sleep; kill -CONT` is armed before the SIGSTOP, so a dropped SSH session or a `kill -9` still gets it back), and nothing is installed or persisted. `zl1-boot-address-selftest.sh` is **24 checks** (with a new self-verifying citation, because the health check's hand-typed counts went stale once) and the new `zl1-address-proof-selftest.sh` is **49 checks** with **ten mutations each failing** -- two of which were green on the first run and exposed real coverage holes (no scenario produced an address without a fresh log line, and none produced a line without the address), and one of which cannot be covered at all (a SIGSTOP that fails to land), which is recorded rather than papered over. Not run on a device: it is in EDL.

- [`docs/ubuntu-touch/115-replacing-a-file-does-not-change-a-process.md`](docs/ubuntu-touch/115-replacing-a-file-does-not-change-a-process.md) — **replacing a file does not change a process, and the retirement gate was about to decide on two facts about two different objects.** `install-netwatch-service.sh --ssh` deliberately restarts nothing (a shell reads its script from the file as it executes it, so the payload is `mv`d over the old inode and the RUNNING watchdog finishes the old build) — which is correct, and which leaves "deployed" and "running" as two different builds until the next boot. After docs 114 the keeper's retirement gate asks for the conjunction of exactly those two (`[ -x ]` + `grep ensure_addrs` on the file, `systemctl is-active` on the process), so it would pass on the OLD build still running while the address-ownership proof — which is the licence for the kill — would correctly fail on it. Hence **`--ssh --activate`**: restart the unit and *prove* it took, by requiring `ExecMainStartTimestampMonotonic` (µs, monotonic) to be strictly later than the `/proc/uptime` read immediately before the restart. Together with "the deployed file carries `ensure_addrs()`" that is decisive — `sh` reads a script before executing it, so a main process started after the file landed read that file. Both clocks are monotonic, so the device's broken wall clock is not involved; an unreadable timestamp, an earlier timestamp (a survivor of the old build) and a service that does not come back active are three different loud failures, and the third says a reboot is not a retry. **What it saves is a reboot, and on this device a reboot is not free**: every boot can end in EDL and leaving EDL takes a finger on the power button for 10–20 s. `zl1-installers-selftest.sh` is **375 checks** (336 before), with a seven-part section that covers every way the check can be wrong, and the fixtures default to the FAILING side. Two self-inflicted wounds are recorded because both came from the same unquoted heredoc that generates the `systemctl` stub: a backquote in a comment made the harness execute a `while :` loop and spin at a full core, and a bare `$1` under `set -u` aborted the `cat` so the stub was never written at all — which reddened 57 checks in sections 1–13 and was announced by one line, `1: parameter not set`. **This window also touched the device**: the user's long press brought it out of EDL into fastboot (serial `33e80afe`), `fastboot reboot` (nothing flashed) booted it, the read-only capture ran, and the phone then went back into EDL during step 06 (the fingerprint probe) about seven minutes in — no installer was run, no partition was written, and `tmp-post-recovery-20260924T013059Z/` holds what was captured.
- [`docs/ubuntu-touch/116-the-existence-test-that-could-not-be-answered.md`](docs/ubuntu-touch/116-the-existence-test-that-could-not-be-answered.md) — **the fingerprint probe's existence tests never got an answer, and the probe spent a boot on the conclusion anyway.** `nsenter -t PID -m -- test -e PATH` switches the mount namespace and *then* execs, so `test` is resolved through the **container's** mount table — which has no `/usr/bin`. `nsenter` therefore exited **127**, the shell read an exec failure as **false**, and "could not run" was reported as "does not exist": section 2's `-> no variant match; AOSP would fall back to fingerprint.default.so` was a conclusion it had not earned. The fix is a read that needs no exec — `/proc/<hal-pid>/root/<path>`, where the **kernel** resolves the path through the target's mount namespace and root and the reading tool is the UT side's own `[ -e ]`/`ls` — applied to all eleven call sites, which also puts the write and its UNDO in the same namespace (before, they named two different places, and the pid in the undo line was a literal from one boot). What the defect *does* add is a negative: since the write never happened, the probe was always **read-only on the device** whatever its own output said. No device involvement this window — the zl1 is still in EDL and the only way out is a physical long press.
- [`docs/ubuntu-touch/117-the-command-that-could-not-run-is-not-a-zero.md`](docs/ubuntu-touch/117-the-command-that-could-not-run-is-not-a-zero.md) — **a command that could not run is not a count of zero, and docs 116's mechanism was one command too broad.** Docs 116 said the fingerprint probe's existence tests failed because `nsenter -m` resolves the command in the container's mount table "where there is no `/usr/bin`". - [`docs/ubuntu-touch/18-stage0-backup-record-2026-09-16.md`](docs/ubuntu-touch/18-stage0-backup-record-2026-09-16.md) — `userdata` and `cache` are now backed up and byte-verified against the device
- [`docs/ubuntu-touch/19-phase1-reproducible-build.md`](docs/ubuntu-touch/19-phase1-reproducible-build.md) — two clean rebuilds produce an identical `halium-boot.img`
- [`docs/ubuntu-touch/21-stage2-first-cold-boot.md`](docs/ubuntu-touch/21-stage2-first-cold-boot.md) — the first `fastboot flash boot` + cold boot: systemd as PID 1, RNDIS up with no drops
- [`docs/ubuntu-touch/22-stage2-coldboot-results.md`](docs/ubuntu-touch/22-stage2-coldboot-results.md) — restoring `/data/system.img` brings the Android container up too; that session ran 20 minutes with `lxc-ls` reporting RUNNING throughout

The earlier EDL incident is resolved; see
[`docs/session-notes/DEVICE-IN-EDL-2026-06-17.md`](docs/session-notes/DEVICE-IN-EDL-2026-06-17.md).
Every script filters on serial `33e80afe` — the unrelated Xiaomi `4a2fe00b` shares the
USB bus and must be ignored.

The known-good v63 image is now rebuildable from tracked source rather than existing only
as a binary, and every rebuild is content-verified against it:
[`docs/ubuntu-touch/24-reproducible-working-image.md`](docs/ubuntu-touch/24-reproducible-working-image.md).

A kernel-side mitigation candidate for the stall is built and reproducible:
[`docs/ubuntu-touch/23-uether-tx-wakeup-patch.md`](docs/ubuntu-touch/23-uether-tx-wakeup-patch.md).

What still does not work: **the device's RNDIS transmit path wedges on about 1 boot in 4.**
It is intermittent, not systematic — 6 of 8 boots in the historical monitor log carried
0.3–1.9 MB, and the one boot right after a stalled one was fine. The device's own `/proc/net/dev` counters show RX
climbing to the end (the host's ARP requests keep arriving) while TX freezes after one
HTTP response. `carrier=1` and `operstate=up` are not evidence that the data path is
alive — that misreading is what produced the earlier "stable for 9 minutes" claim. See
`22-stage2-coldboot-results.md` §5.

**The device exposes only RNDIS, not adb**, so everything after a boot is done over SSH
(`ssh root@10.15.19.82`) or, when the device is in recovery, over adb. The device-side
watchdog is installed, SSH works, and cold-boot trials are now driven end to end over SSH
by [`scripts/run-stage24-and-25.sh`](scripts/run-stage24-and-25.sh) — including the
reboots, which is what the earlier adb-based driver could not do.

The step that was missing is on **this** side of the cable. A trial is only a trial once
the host's `usb0` is configured; with nothing at the other end the device records
`rx_packets=0` for its whole life and looks exactly like a stall. Every trial now starts
[`scripts/host-watch-usb0.sh`](scripts/host-watch-usb0.sh) first and waits for the host to
see `usb0` go away and come back. See
[`docs/ubuntu-touch/37-the-trial-that-had-no-peer.md`](docs/ubuntu-touch/37-the-trial-that-had-no-peer.md).

The running tally of Stage 2.4 trials, and which of them count, is in
[`docs/ubuntu-touch/stage2-coldboot-trials.md`](docs/ubuntu-touch/stage2-coldboot-trials.md).

## Historical track: BlackBerry 10 / QNX and BlackBerry Android

Earlier notes evaluated whether BlackBerry 10 / QNX or BlackBerry Android could be ported to `zl1`. Those tracks are currently paused. Existing reference clones under `references/` are research material only and are not a working `zl1` build tree.

## Goals

- Document the target device hardware, boot chain, partition layout, and firmware constraints.
- Preserve reproducible notes, manifests, scripts, and artifacts used during investigation.
- Prefer read-only inspection and reversible steps before any flashing or partition writes.
- Back up critical partitions before any write operation.

## Safety notes

- Do not flash anything until critical partitions are backed up and checksummed.
- Do not write to modem/EFS/persist-related partitions during experiments.
- Prefer `fastboot boot` over `fastboot flash` when the bootloader supports it.

  *Superseded 2026-09-16.* `fastboot boot` was the main testing method through v2–v73 and
  it is the reason those sessions produced so little: it does not persist, it leaves
  dirty state, and it twice dropped the device into EDL. Write `boot` with
  `fastboot flash boot` instead, and rely on the verified rollback image plus a known way
  into fastboot/TWRP. See
  [`docs/ubuntu-touch/17-adaptation-plan.md`](docs/ubuntu-touch/17-adaptation-plan.md) §1.5.
  `system`, `vendor`, `userdata`, and the modem/EFS partitions still must not be flashed
  until the restore procedure is written down.
- Keep the Android restore path documented before testing Ubuntu Touch images.
