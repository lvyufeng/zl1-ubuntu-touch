### What to do about the device

1. **Plug it into a charger and leave it** for a while. A phone that is off or flat
   presents nothing on USB, which is exactly what the host sees now.
2. Then power it on and hold **Volume Up + Power** for TWRP. The waiting job will do the
   rest without further input.

There is nothing on the device to lose: the boot partition holds the debug-shell image it
has been booting successfully, and the stock `boot.img` rollback is verified and untouched.

### Corrections since the last status

A reachable window was finally caught (docs/ubuntu-touch/27-what-a-reachable-window-shows.md)
and it corrected three things this page had been asserting:

- **not "about 1 boot in 4 stalls"** — every boot is reachable for its first ~50 s and

Two things it confirmed as *better* than expected: netwatch is installed and running, and
the Android container comes up with its full HAL set — fuller than the 2026-06-13 record.
sshd is listening on 22.

## What the last boot revealed

The watchdog's first real outing produced the finding the previous two days were
missing ([`26`](26-gadget-reassert-every-2-minutes.md)):

> The v63 keeper re-enumerates the device's USB gadget **every ~118 seconds** —
> 16 times in 36 minutes, measured — because every time it kills an interfering
> USB manager it also rebuilds the gadget. Each rebuild destroys the host's
> `usb0`. Of those 36 minutes, 2 pings got through.

That one fact explains the "reachable for ~30 seconds" wall every June session
hit, and it means the u_ether transmit-wakeup patch
([`23`](23-uether-tx-wakeup-patch.md)) is probably **not** the cause after all —
it fixes a real defect, but probably not this failure.

A fix is built and verified to differ from v63 in exactly one initramfs file:

```
halium-boot-zl1-v63-noreassert.img   18,010,112 bytes   d1f4fe29e282792b…
```

## Why the device is unreachable, and why that is hard

It exposes RNDIS and **not adb**, its HTTP status page is read-only, and the link
works only in the short windows between gadget rebuilds. Nothing can be read out
of it and nothing can be commanded through it. Five host-side levers were tried:

| Attempt | Result |
| --- | --- |
| `modprobe -r rndis_host` then reload | usb0 re-registers, link still dead |
| `/sys/bus/usb/devices/3-3/{unbind,bind}` | same |
| `authorized` 0 → 1 | same — and the device's host MAC changed, so its gadget did rebind |
| `USBDEVFS_RESET` — a real bus reset | same, and dmesg confirms the device re-enumerated |
| runtime PM suspend/resume | not possible: `runtime_status` stays `active` |

So: **one physical action.** Power off, then hold **Volume Up + Power** for TWRP.

## What that press sets off

`twrp-one-shot-setup.sh` is already waiting and armed with the new image. On
reaching TWRP it will, without further input:

1. back up `misc` (the 2026-06-07 set has no image of it)
2. install the **fixed** watchdog — the previous one could not fire when it
   mattered, because it waited for the host to generate the traffic it was
   watching for; it now probes the host itself
3. fix SSH public-key login (`AuthorizedKeysFile /etc/ssh/authorized_keys.d/%u`)
4. flash `halium-boot-zl1-v63-noreassert.img` — the actual fix
5. boot it, with a recovery fallback set 30 minutes out

The next boot is therefore the real test: if the gadget stops being rebuilt, the
link should stay up and the device becomes reachable over SSH and HTTP for as
long as it is powered on. If it works, `rm /userdata/zl1-netwatch-reboot-recovery`
over SSH cancels the fallback reboot. If it does not, the device returns itself
to TWRP and the log gets read without another press.

## The immediate next steps, in order

1. **Human:** Volume Up + Power → TWRP. Everything below follows.
2. Confirm the link is stable: re-enumeration count near zero, and SSH answers
   for minutes rather than seconds. This is the decisive measurement.
3. If SSH works, every later step is far cheaper — reboots, log reads and file
   edits stop needing TWRP at all.
4. Stage 2.4 (three consecutive cold boots) — `stage2-coldboot-trial.sh` records
   each one; the criterion has never had a record behind it.
5. Stage 2.5 (rollback drill) — `stage2-rollback-drill.sh`, which is what turns
   "there is a verified rollback" from a claim about a file into one about the
   device.
6. Then re-evaluate the u_ether patch on a link that is actually stable.

  [`24`](24-reproducible-working-image.md)
