### What to do about the device

1. **Plug it into a charger and leave it** for a while. A phone that is off or flat
   presents nothing on USB, which is exactly what the host sees now.
2. Then power it on and hold **Volume Up + Power** for TWRP. The waiting job will do the
   rest without further input.

There is nothing on the device to lose: the boot partition holds the debug-shell image it
has been booting successfully, and the stock `boot.img` rollback is verified and untouched.

### Corrections since the last status

A reachable window was finally caught (docs/ubuntu-touch/27-what-a-reachable-window-shows.md)
and it corrected three things this page had been asserting:

- **not "about 1 boot in 4 stalls"** — every boot is reachable for its first ~50 s and
  unreachable after. A 10-minute measurement found one 47 s window whose device uptime was
  9.73 s. It is a schedule, not a probability.
- **the debug-shell image does not give a shell.** The flag reaches the ramdisk, but
  busybox telnetd exits rc=1.
- **the recovery fallback had never worked.** The heal branch ended in `continue`, which
  skips the recovery check below it; with the marker at 900 s the device ran to 2870 s
  without one attempt. Fixed.

Two things it confirmed as *better* than expected: netwatch is installed and running, and
the Android container comes up with its full HAL set — fuller than the 2026-06-13 record.
sshd is listening on 22.

## Why this is hard to reach

The device exposes RNDIS and **not adb**, its HTTP status page is read-only, and the
link is only usable in the first ~50 seconds of a boot. Five host-side levers were tried
to bring it back mid-session, all ineffective:

| Attempt | Result |
| --- | --- |
| `modprobe -r rndis_host` then reload | usb0 re-registers, link still dead |
| `/sys/bus/usb/devices/3-3/{unbind,bind}` | same |
| `authorized` 0 → 1 | same — and the device's host MAC changed, so its gadget did rebind |
| `USBDEVFS_RESET` — a real bus reset | same, and dmesg confirms the device re-enumerated |
| runtime PM suspend/resume | not possible: `runtime_status` stays `active` |

Nothing here is broken beyond recovery, though: the boot partition boots, the rollback is
verified, and the device has never been left in EDL.

## What the churn actually is

[`26`](26-gadget-reassert-every-2-minutes.md) measured the keeper rebuilding the USB gadget
every ~118 s, and [`27`](27-what-a-reachable-window-shows.md) found a second party: a
`lxc-stop -n android -k` in the process table. So roughly 50 seconds into each boot,
something starts repeatedly rebuilding the gadget and stopping the container.

The fix under test removes the keeper's half of that:

```
halium-boot-zl1-v63-noreassert.img   18,010,112 bytes   d1f4fe29e282792b…
```

verified to differ from v63 in exactly one initramfs file.

## The fix has already been flashed — it needs a charge

At 16:30 the waiting job fired: it installed the watchdog in record-only mode, re-applied
the SSH fix, flashed `halium-boot-zl1-v63-noreassert.img`, and rebooted.

The device got as far as `fastboot reboot` and then went silent:

| host time | what the host saw |
| --- | --- |
| 16:31:00 | `fastboot reboot` → `OKAY` |
| ~16:32 | the pre-bootloader USB dance: `18d1:4ee7` (LEX727), `18d1:4ee2`, `18d1:d00d` (Android) |
| 16:32:07 | last USB event of any kind |

Nothing since — seven minutes after the flash, then fifteen. No RNDIS, no adb, no
fastboot, no EDL. `d00d` is the bootloader's own descriptor and it appeared, so the flash
did not break the boot chain; the device simply stopped presenting itself.

Note what did **not** happen: nothing re-enumerated. The gadget churn that
[`26`](26-gadget-reassert-every-2-minutes.md) measured has not recurred, which is
consistent with the flashed image being the one without the keeper's re-assert — but it is
equally consistent with a device that has stopped booting, so it is not evidence yet.

The likely explanation remains the battery. It ran a full Android container plus hours of
USB churn, and a phone that has shut down presents nothing on USB. There is no way to know
from here: the netwatch log does record `power_supply` capacity in its snapshot, but only
if a boot reaches uptime 120 s, and this one did not get that far.

**So: charge it.** Plug it in and leave it a while, then power on and hold
**Volume Up + Power** for TWRP. A job is already waiting and will repeat the same sequence
from step 1, so nothing was lost — it is idempotent.

## What the next boot will be measured by

**Not "does SSH connect"** — the window in every previous boot was too short for that to
be the first thing that shows up. The test is whether the link is still there past uptime
120 s, and then still there at 600 s. `measure-link-stability.sh` reports exactly that:
re-enumerations, reachable fraction of time, longest continuous reachable run.

The baseline to beat, measured on v63 over 10 minutes: **6 re-enumerations, 7.8%
reachable, longest run 47 s, and that run was at device uptime 9.7 s** — i.e. the first
and only window.

If the link survives, SSH follows and every later step stops needing TWRP.

## The immediate next steps, in order

1. **Human:** Volume Up + Power → TWRP. Everything below follows.
2. Confirm the link is stable: re-enumeration count near zero, and SSH answers
   for minutes rather than seconds. This is the decisive measurement.
3. If SSH works, every later step is far cheaper — reboots, log reads and file
   edits stop needing TWRP at all.
4. Stage 2.4 (three consecutive cold boots) — `stage2-coldboot-trial.sh` records
   each one; the criterion has never had a record behind it.
5. Stage 2.5 (rollback drill) — `stage2-rollback-drill.sh`, which is what turns
   "there is a verified rollback" from a claim about a file into one about the
   device.
6. Then re-evaluate the u_ether patch on a link that is actually stable.
