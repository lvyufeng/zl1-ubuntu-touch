# 149 — 一次启动的每一步都有上界，可两个归档步骤的上界比被调者自己的最坏情况小 5.0 倍和 3.5 倍，还有一个根本没有上界

**日期**: 2026-09-24
**状态**: 本轮**没有碰设备**（设备仍在 fastboot，`battery-soc-ok:no`，见 §8）。这一页动的全是
**主机侧、离线**的代码：`scripts/host/zl1-one-boot-runbook.sh`（一次启动那条命令）的上界算术、
`scripts/host/zl1-heat-fix-chain.sh`（那条链）里**唯一一个没有上界的调用点**。三个缺陷，一个比一个隐蔽：

1. **算错的上界。** runbook 给每个步骤套**一个** `timeout -k 5 $STEP_LIMIT`（默认 **900 秒**），
   可是两个**会归档**的步骤（`01-capture`、`03-heat-chain`）跑的是**整个被调者**，而被调者是有结构的：
   capture 有 **18** 个设备步骤、每个自己 **240** 秒 ⇒ 最坏 **4530 秒**；
   链是 settle + 5 个步骤位点 + 2 个有上界的 scp + proof + A/B 两个窗口 + 4 次回读 ⇒ 最坏 **3145 秒**。
   **5.0 倍和 3.5 倍**。而 900 这个数**从它被写下的那一天起就不够**（§2）。
2. **没有的上界。** 链自己的 `04-proof` 用的是裸 `"${SSH[@]}"` 和裸 `"${SCP[@]}"`——
   **它自己文件头里"每个步骤都有墙钟上界"这句话，对它来说是假的**，而它恰好是那条链上
   **在手机上跑得最久**的那一步（§4）。
3. **匹配不上的断言。** eeprom 那个 harness 里有两条断言**永远无法通过**，而它和探针是
   **同一个提交**一起上的——HEAD 是红的，而红的那两条看上去像"覆盖"（§7）。

## 1. 一句话结论

| 问题 | 答案 |
|---|---|
| 这一页在修什么？ | 一次启动那条命令的**上界算术**。它给每个步骤套**一个** `timeout`，可两个会**归档**的步骤跑的是**整个被调者**，而被调者的最坏情况是**它自己的结构**决定的：capture 是 `设备步骤数 × (它自己的每步上界 + 5) + 120`，链是 `settle + (步骤位点 + 有上界的 scp) × (每步上界 + 5) + proof + A/B 窗口 + 回读次数 × 回读上界 + 余量` |
| 那两个数字分别是多少？ | capture **4530 秒**（18 × 245 + 120）；链 **3145 秒**（90 + 7 × 305 + 180 + 240 + 260 + 240）。默认 **900** |
| 所以后果是什么？ | **5.0 倍和 3.5 倍。** 一次启动是**用一个手指换来的**（10–20 秒长按电源键，而且 EDL 出来也要按），而 900 秒到了之后 SIGKILL 落在**归档步骤的中途**：那一轮的 `04-health-check` 和 `04b`–`04n` 那整组探针——**这次启动正是为了读它们才花的**——一个都不落盘 |
| 900 是哪来的？ | commit `f2f3582`（"两个链的每一步都没有时钟"），同一批把 capture 的每步上界定成 240 秒。**它不是坏值，是会过期的值**：capture 从 7 个设备步骤长到 18 个，它就小了 |
| 那它当时够吗？ | **不够。** 那天 capture 的 7 个设备步骤最坏就是 7 × 245 + 120 = **1835 秒**，已经是 900 的 **2.0 倍**。也就是说这不是"被调者后来长胖了"——**900 从来没覆盖过它包住的那一步** |
| 为什么不干脆把默认值调大？ | 因为那只是把同一个缺陷挪到下一次：默认值是**地板**，被调者的算术才是那一层要用的数。**算得出来的东西不该由人来猜** |
| 还有一处没有上界？ | **链的 `04-proof`。** 它的 ssh 和 scp 都是裸调用，所以链自己文件头那句"每个步骤都有墙钟上界（见 `bound()`）"对它**不成立** |
| 设备端那个 `timeout -k 5 120` 不就够了吗？ | **不够，而且这是最容易看错的一处。** 它限制的是**手机上的那个程序**，本地的 ssh 一点都不受它管——RNDIS 停住时阻塞在 `read()` 里的是**本地这一头**。所以那一步当时唯一会结束它的是**调用者**的兜底，而兜底一响，这次启动后面要读的东西全没了 |
| 修法是什么？ | ① 两个归档步骤的上界**从被调者身上读出来**（`_cap_shape` / `_chain_shape`），取 `max(地板, 算出来的)`，把**算式**印出来；② proof 的 scp 和 ssh 都进 `bound()`，上界 = 设备侧上限 + 一次回读的余量；③ **读不到形状 ⇒ UNUSABLE，不是通过**，步骤保留地板**并且说它没有被覆盖** |
| 这件事的语义为什么是"地板"？ | 因为 `--step-limit 2` 的时候，`01-capture` 仍然拿到**它算出来的那个数**（harness 的替身是 3 个设备步骤，所以 855 秒；换成真文件就是 4530 秒）：计算值只能**放宽**一个步骤，不能收紧它。人给的数和结构给的数，谁大听谁的 |
| 还有别的吗？ | 写这一节的 harness 时**翻出两个旧缺陷**（§6）：`--skip` 会让"计划与执行不一致"在**每一次** skip 上报错（而拒绝分支自己给的建议就是 `--skip`），并且那个诊断调用了 **harness 的** `bad`，于是它在步骤自己的文件里印 `bad: command not found` |
| 第三件呢？ | eeprom 那个 harness 有**两条永远匹配不上的断言**，而且是和探针**同一个提交**一起上的（§7）——**一条永远不会红的断言比一条红了的断言更坏**，因为它被当成覆盖 |

## 2. 三个数字，和被调者的形状

| 步骤 | 谁在跑 | 被调者的最坏情况怎么算 | 数字 |
|---|---|---|---|
| `01-capture` | `zl1-post-recovery-capture.sh` | 18 个设备步骤 × (自己的 `STEP_LIMIT` 240 + 5) + 120 余量 | **4530 秒** |
| `03-heat-chain` | `zl1-heat-fix-chain.sh` | settle 90 + (5 个步骤位点 + 2 个有上界的 scp) × (300 + 5) + (proof 120 + 回读 60) + (2 × 30 + 120 + 60) + 4 次回读 × 65 + 240 余量 | **3145 秒** |
| `02` / `04` / `05` | 一次 installer 调用 | 自己没有可读的结构（它不调别的脚本） | 900（地板） |

`f2f3582` 那天的 capture：7 个设备步骤 × 245 + 120 = **1835 秒**，对着地板 900——**2.0 倍**。
今天 18 个步骤 ⇒ 5.0 倍。链这边同理：docs 128 给同一个步骤加进了 A/B 测量，
一个 `--ab-hold` 就 120 秒，加上两个窗口和 4 次回读，于是它也超了（3.5 倍）。

**为什么"最坏情况"是这里唯一诚实的口径？** 因为这整族上界存在的理由**就是**停机：正常一轮每一步几秒钟，
而**RNDIS 停住**的时候每一步都会撞到它自己的设备端上界。上界要覆盖的是**那种**一轮，不是顺利的那种。
按顺利的一轮定上界，等于在出问题的那一轮里把归档掐死——**恰好是最需要那份归档的时候。**

## 3. 修法一：从被调者身上读，并且把算式印出来

三个动作，都在这棵树的既有习惯里：

**（a）读被调者的数，从被调者的文件里读。** `host_ready()` 早就在读那几个被调者的路径了，
这里是同一件事往下走一层：`_cap_shape()` 数 capture 里 `step … device` 的行数、取它自己的 `STEP_LIMIT`；
`_chain_shape()` 数链的步骤位点、有上界的 scp、`read_state` 的次数和它那六个数字。
**形状的每一格都必须读出来是数字**，任何一格读不出来就整个算不出来——不猜、不默认。

**（b）`max(地板, 算出来的)`，所以标志位是地板，计算值只能放宽。**
`step_bound()` 返回两者里大的那个，于是 `--step-limit 2` 不会把一个 4530 秒的步骤砍成 2 秒：
harness 断言的就是这一条——替身（3 个设备步骤）在 `--step-limit 2` 下仍然拿到它算出来的 **855 秒**，
而不是被要求的 2 秒。
数字印在**三个地方**，因为它们回答三个不同的问题：计划里（跑之前就该知道）、
`--status` 的四行表里（只读，问"这一步会被砍吗"）、归档的 `INDEX.txt` 里
（**`124` 只有在产生它的那个数旁边才读得懂**）：

```
bound per step: 02/04/05 = 900s (--step-limit)
                01-capture = 4530s  the callee's own 18 device steps x (240+5) + 120 of slack
              03-heat-chain = 3145s  settle 90 + (5 step sites + 2 bounded scps) x (300+5) + ...
```

**（c）"读不到形状"是 UNUSABLE，不是通过。** 这是这棵树的旧账
（[`137`](137-a-boot-should-answer-the-question-nobody-asked.md) 那一段里的五种"报不出自己要说的话"的仪器）：
一个算不出来就**安静地退回地板**的检查，看上去和"覆盖了"一模一样。所以形状读不出来时，
`--status` 那一行明说 `THE CALLEE SHAPE COULD NOT BE READ -- this is the flat --step-limit, and the step
is NOT covered`，跑之前的主机检查把它走 **UNUSABLE** 通道（**不是** pass），归档里那一行也写 `NOT COVERED`。

## 4. 修法二：那个一直没有上界的步骤

链上每个步骤都走 `bound "$STEP_LIMIT" …`，**除了** `04-proof`：它的 scp 和 ssh 都是裸的
`"${SCP[@]}"` / `"${SSH[@]}"`。这不是风格问题，是**语义**问题：

- 设备端那句 `timeout -k 5 120` 限制的是**手机上跑的那个脚本**（`zl1-address-owner-proof.sh`），
  **本地的 ssh 完全不受它管**。RNDIS 停住时，卡在 `read()` 里的是本地这一头，`timeout` 在另一头数秒。
- 所以那一步没有上界时，**唯一**会结束它的是**调用者**的兜底 `timeout`。
  而兜底一响，紧接着的就是"这次启动剩下的读数全丢"——一条只会在停机时被触发的路径，
  **停机正是它的触发条件**。

改成两步都进 `bound()`，并且上界**算出来**：

```sh
PROOF_DEV_LIMIT=${ZL1_PROOF_DEV_LIMIT:-120}
PROOF_LIMIT=$(( PROOF_DEV_LIMIT + STATE_LIMIT ))     # 设备侧那个数 + 一次回读的余量
```

印出来的样子是 `bounded at 145s (the device-side 120s plus 25s of link slack)`
（harness 用 `--state-limit 25` 驱动这一行，就是让"它确实是算出来的"变成可读的）。
另外两条静态断言把这件事钉住：`bound "$PROOF_LIMIT" "${SSH[@]}"` 这个**包法**在**出厂文件**里存在，
而且**整条链里不再有任何没有上界的 ssh 或 scp 调用点**——一条将来新增的调用点会让它变红。

## 5. 这条断言要怎么写，才不是在证明自己

三件事，缺一个这条检查就变成装饰：

1. **替身必须带上被调者的形状。** 原来那两个 fixture 是空壳的"我跑完了"，
   对它们做减法当然什么也测不出来。现在 CAPTURE 的替身里带着 `STEP_LIMIT=240` 和 3 行
   `step … device`，HEAT 的替身带着它那六个数和 `step` / `read_state` 的行数——
   **形状不是被调者旁边的东西，形状就是被调者的读数。**
2. **第二个实现，跑在真文件上。** harness 里另写了一遍同样的算式（`_shipped_num` + 那两个 `grep -c`），
   直接读**仓库里那两个真脚本**，算出来 `capture 4530s / chain 3145s / 默认 900s`，
   并且断言前两个**大于**第三个。**为什么要两遍**：同一份实现算错了两次是同一个错误，
   而这里要回答的问题是"900 到过底够不够"——那是一个关于**真文件**的事实问题。
   顺带它还是一个**到期检查**：将来有人把默认值调到 4530 以上，或者 capture 又长出十个步骤，
   这一条就会红，而红的时候必须有人出来说为什么。
3. **两个 mutation，各证明一半。** `noboundshape`（让算出来的数变成空）必须让"没被覆盖"这句话出现——
   证明**退回地板不是安静的**；`skipalarm`（把 `skip` 从 `EXECUTED` 里放回去）必须让计划不一致的告警回来
   （见 §6）。两个 mutation 都要先证明**改到了出厂文件的那一行**，并且改完之后**能解析**。

## 6. 写这一节时翻出来的两个旧缺陷（都在同一条分支上）

两个都不是这一轮引入的，是**新的断言把一条从没被走过的分支走了一遍**才看见的：

1. **`--skip` 会让"计划与执行不一致"在每一次 skip 上报错。**
   `EXPECTED`（声明的顺序）和 `EXECUTED`（记录的每一行）比，而 `EXECUTED` 里**含着 `skip` 的行**——
   所以任何一次 `--skip` 都会打印 `THE PLAN AND THE RUN DISAGREE` 并退出 1，
   **而拒绝分支自己给操作者的建议就是"用 `--skip`"。** 修法是把 `skip` 从 `EXECUTED` 里排除：
   归档仍然完整地记录 skip 这一行，参与比较的只是**真正跑过**的步骤。
   （在 HEAD 上量过：`--yes --skip 03-heat-chain` ⇒ `4 step(s) ran, 1 failed`，rc=1。）
2. **那条诊断调用的是 harness 的 `bad`，不是脚本自己的 `say`。**
   于是它印出来的四行是 `bad: command not found`，落在**步骤自己的文件**里，没有一个字是诊断。
   这正是这一轮翻来覆去遇到的那个形状：**一个报不出它存在理由的仪器**。
   改成 `say`，并且加一条静态断言盯着**出厂文件**里没有这个调用（`notwant 'bad "'`）。

## 7. 两条永远匹配不上的断言，而它们是随提交一起上的

`25fef41`（上一轮最后一块缺口）里，探针和 harness 是同一个提交新增的。harness 里有两条：

- `want 'sysfs_create_bin_file\(\) is the LAST thing'` —— 而探针把这句印在**两行**上：
  `… is the LAST` / `FALLIBLE thing at24_probe() does …`。**跨两行的短语永远匹配不上。**
- `want 'a statement before it failed'` —— 而那条 verdict 写的是 `something before it failed`。

也就是说：**HEAD 是红的**，而红的那两条看上去像覆盖。**一条永远不会红的断言比一条红了的断言更坏**：
红了的断言会有人去修，永远不会红的断言会被当成"这块测过了"。
哪一边动？**探针那边动**。因为要求本身是对的（"点到那个调用**和它的位置**"），
而一个总线之外的兄弟——`zl1-fm-radio-probe.sh`——就是把整句印在一行上的：
`video_register_device() is the LAST thing silabs_fm_probe() does, after the regulators, the`。
所以是这一块钱的散文偏离了它兄弟的形状，而 harness 的要求正是照着那个形状写的。
修完 **285 项全绿**，而且健康检查里那个"285 项"的引用**本来就是对的**——
它一直在引用一个红的 harness 的数。
