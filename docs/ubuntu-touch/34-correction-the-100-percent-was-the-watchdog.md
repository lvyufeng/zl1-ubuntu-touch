# 34 — 更正：那个 100% 是看门狗制造的

**日期**: 2026-09-18
**作废**: [`32`](32-counterexample-38-minute-boot.md) 的"45 分钟 100% 可达"及其推论，
以及 [`33`](33-the-container-restart-loop.md) 建立在它之上的对照。

---

## 1. 一次只差一个开关的对照

同一张镜像（v63）、同一天、同一个 45 分钟长测脚本：

| | `heal=1`（9/18 04:33 那次） | `heal=0`（9/18 14:30 那次） |
| --- | ---: | ---: |
| 主机侧可达率 | **100%**（2698s / 2698s） | **0.3%**（2 / 680 个采样） |
| 主机侧重新枚举 | **0 次** | **0 次** |
| usb0 MAC | 全程不变 | 全程单一值 `36:f7:e9:0c:86:ad` |
| 设备侧 STALL | 8 次 | 待读 |
| 设备侧治愈 | 24 次 | 0（关掉了） |

**两次的开机后头一分钟都是可达的，然后就没有了。** 差别只在看门狗开不开。

## 2. 我错在哪

那次 `heal=1` 的开机，设备端日志写得很清楚：

```
 102.36s STALL: host unreachable for 46s; iface=rndis0 tx_pkts=99 rx_pkts=164
 102.78s HEAL A: enable=0/1 on the gadget
 187.27s STALL: host unreachable for 46s; iface=rndis0 tx_pkts=10 rx_pkts=106
 187.47s HEAL B: unbind/rebind the rndis function
 ...每 ~84 秒一次，共 8 次 STALL、24 次治愈
```

**它一直在卡，是看门狗每 84 秒把它救回来的。**

而我读主机侧的 `100% 可达` 时没有去看设备端日志，于是把"治愈成功"当成了"没有故障"，
还基于它写了：

- `32`："容器停在 zygote 之前 → 链路 100% 可用"
- `33`："稳定的链路目前是 Android 启动失败的副产品"

**那个对照是拿一个被治愈污染的样本去比一个没被污染的样本。** 结论作废。

## 3. 更根本的问题：我用一个会自愈的工具去测量它自愈的故障

这已经是同一个错误的**第三种形态**：

| 时间 | 形态 |
| --- | --- |
| 9/17 | 看门狗的治愈被我误判成 keeper 的行为（[`26`](26-gadget-reassert-every-2-minutes.md) → [`29`](29-correction-watchdog-not-keeper.md)） |
| 9/18 早些 | `--noheal` 只放在环境变量里，安装脚本从 `$2` 读，所以根本没生效 |
| 9/18 现在 | `heal` 开着跑测量，把治愈后的稳态读成链路健康 |

**一个会对自己观察的现象动手的仪器不是仪器。** 现在的做法是：

1. 装的时候显式传 `--noheal`
2. **在设备上验证 marker 文件真的存在**，不信安装脚本自己的"成功"消息
3. 判据从"主机能不能 ping 通"改成**"设备侧记了几次 STALL"**——治愈关掉后，卡就是卡

## 4. 修正后的图景

| | |
| --- | --- |
| **链路** | 开机头约 1 分钟可用，之后**收得到、发不出**，**不会自愈**（纯记录下 5 分钟、45 分钟都没恢复） |
| gadget 层 | 全程健康：`d001` 一直在、MAC 不变、0 次重新枚举 |
| 卡死的签名 | 包在设备队列**之前**被丢掉（[`30`](30-outbound-drops-before-the-queue.md)）—— 这条没被推翻 |
| 看门狗 | **能把它救回来**（每次 enable=0/1 或 rebind 之后链路恢复），但代价是每 84 秒一次中断 |
| 仍然未知 | 为什么首次断，以及 netd 是不是那个东西 |

值得记一句：**"看门狗能救回来"本身是有价值的信息**——它说明故障不是不可逆的硬件态，
是一个可以被重新枚举清掉的软件态。这和 [`22`](22-stage2-coldboot-results.md) §5.2d
"主机侧五种手段无效"并不矛盾：主机做不到的事，设备侧 rebind 函数（重建 netdev）做到了。

## 5. 自回 TWRP 失败了

marker 写了 2700 秒，设备过了关口也没回 TWRP。

```
在 TWRP 里写 misc → 成功（实测读到 'boot-recovery'）
在 UT  里写 misc → 不成功（9/17 那次是 "could not write"，这次是根本没动）
```

**这条现在是两票。** 说明容器起来之后，`printf > /dev/block/sda4` 这个动作在 UT 里
是失败的（可能是 SELinux/apparmor，也可能 misc 被占用）。

所以"一次按键之后全自动"目前做不到——每次读日志还是要按键。

## 6. 下一次进 TWRP 时应该做什么

既然能提前做，就在 TWRP 里把该做的都做完：

1. **装纯记录看门狗**（已验证机制）
2. **把 netsnap 那十次快照确认到位**（`ip rule` / `ip route get` / iptables 计数器）
3. 开机，让它卡，**不救**，45 分钟后读日志

目标是拿到**第一个不被污染的、带 netfilter 现场的卡死样本**。
那才是能定位 B（为什么发不出去）的证据。
