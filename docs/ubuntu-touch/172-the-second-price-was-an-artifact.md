## 2. 这一趟跑的是什么，以及它为什么值得跑

docs 171 修完两个缺陷之后，仪器**一次都没上过设备**。这一趟买的是**两件只有真设备能回答的事**：
那个"等"到底会发生什么，以及**改完之后判词会不会变**。

"等"发生了，而且**它自己就是这一趟最有用的一条读数**：

```
== the wait -- does window A's reading come back before the control window reads it?
   window A's hottest tsens zone: 49.6 C. Waiting up to 240s (every 10s) for it to come
   back to within 0.5 C of that before window C reads anything.
   IT CAME BACK: 45.4 C after 10s, against window A's 49.6 C (margin 0.5 C). Window C
   below is therefore a CONTROL and not a second reading of the same heat.
```

**"10 秒"这件事本身就是答案**：一台真的被干预加热、需要时间散热的手机，不会在第一个采样点就"回来"。
10 秒回来只说明一件事——**它本来就在往下走**。而这句话被印在一段宣称"窗口 C 因此是一个控制"的文字
正上方，那条结论就是从这里开始错的。

## 3. 判词是 `COST-MEASURED`，而它的三个数字**自己**说明它为什么不是价钱

判决那一段印的是：

```
   the largest warming from A to B on any tsens zone: 3.5 C  (thermal_zone9 (tsens_tz_sensor8))
   and from A to C (the control, same state as A):   0.3 C  (thermal_zone16 (tsens_tz_sensor15))

   -> COST-MEASURED: pinning all four cores warmed the hottest tsens zone by 3.5 C ...
```

而**完整表**（这一趟它真的全印出来了，38 行）的第 1 行和第 2 行是另一个故事：

```
   thermal_zone12 tsens_tz_sensor11        49.6   47.0   41.9   -2.6   -7.7
   thermal_zone11 tsens_tz_sensor10        48.3   46.7   41.9   -1.6   -6.4
```

三件事一起读：

1. **A 那一列里最热的两条，在 B 和 C 里一直在掉。**A 的最热是 `thermal_zone12` 的 49.6；
   到 B 它掉到 47.0，到 C 掉到 41.9。**这一趟的手机是刚从一段负载里出来、正在快速降温**。
2. **B-A 是正的 22 行、负的 2 行，而负的那两行是 tsens 里最热的两条。**所以那句
   "the largest warming from A to B on any tsens zone" 里的 **3.5 °C，是 19 个小正数里最大的那一个**，
   不是"这个成因值多少"。钉住四核加进去的热，在**最热的传感器**上甚至没有盖过这一趟的下降。
3. **控制窗口 C 的最热 zone 比 A 低 7.7 °C**，而判决拿它去比的那个数（**C-A 的最大值**）是 **0.3 °C**。
   0.3 之所以小，是因为**整台手机凉了**——**最大值是在 zone 之间取的，而 zone 的排名在这一趟里换过手**。
   于是"控制窗口只高了 0.3 °C"这句话被读成了"升温回来了"。

**这三个数字放在一起，只能支持一个结论**：这一趟测的是**手机的漂移**，不是 governor。
而仪器**把它印成了后者**——只因为它问的三个问题都不是"这台手机现在站着不动吗"。

## 4. 缺陷一：那个比较是**单向**的

判据在代码里是一行：

```sh
if awk -v a="$W_A" -v n="$W_NOW" -v m="$MARGIN" 'BEGIN { exit ((n - a) <= m) ? 0 : 1 }'
```

`n - a <= m`。**只要往下走，它就永远成立**——手机掉 4 °C、掉 40 °C，都算"回来了"。
一个差值可以是**两个相反的故事**（干预的热没散掉 vs. 手机自己凉了），而这一行**只判一个方向**，
所以它把第二个故事**读成了第一个故事的失败**，也就是读成了"回来了"。

这不是一个边界情况：**这一趟第一次采样就命中了它**，于是 240 秒的等待上限一次都没用到。
docs 171 写这个等待时的原话是"等的是**读数回来**"——而"回来"这个词里**本来就含两个方向**，
代码里只有一个。

---

## 5. 缺陷二：它比的是"**最热的那个 zone**"，而那个身份**是会换手的**

等的那一段比的是 `hot_tsens`——**这个输出里最热的 tsens zone 是几度**。这句话看起来
"接着上一句"，其实换了一个主语：`window A's hottest tsens zone` 和 `this sample's hottest tsens zone`
**不一定是同一个 zone**。

这一趟就是：A 的最热是 `thermal_zone12`（49.6），而第一个采样点的最大值是 **45.4**——
**那个 45.4 属于另一个 zone**（12 号此时已经掉到 45 以下了，因为它掉得比别人快）。
换句话说，这一行代码**拿一个 zone 的数字和另一个 zone 的数字相减，把差当成了"回来"**。
它没有说它在这么干，而输出里也看不出——除非把 38 行表整个读一遍。

**这两个缺陷加起来就是这一趟的全部故事**：手机在掉，掉得还不均匀，
而那个检查既不问方向、也不问"是不是同一个 zone"。

---

## 6. 缺陷三：窗口 A 是读在**一条曲线**上的，而等待只在 C 之前有

docs 171 加的"等"是"在开 C 之前等"。**A 之前什么都没有**——所以：

```
   A  49.6      B  47.0      C  41.9
   ↑ 读在一条每十秒掉 4.2 °C 的曲线上
```

三个窗口是**同一条下降曲线上的三个点**。而"控制窗口"这个概念的全部意义是"A 和 C 是**同一个状态**"——
**如果 A 自己不是一个状态，C 再准也控制不了任何东西**。

这一条比前两条更靠前，也更难自己暴露：**前两条都在比较里，这一条在比较开始之前**。
而且它解释了前两条为什么会在**同一趟里同时**命中：一台正在快速降温的手机，
正好让"单向比较"和"最热 zone 换手"**同时**成立。

---

## 7. 三个缺陷是**一个**：没有任何一条检查问过"这台手机是不是站着不动"

把三条排在一起：

| | 问题 | 它该问的 |
|---|---|---|
| 一 | "回来"只判了往上的方向 | **差值大不大**（绝对值），不是"是正是负" |
| 二 | 比的是两个窗口各自的**最热 zone** | **同一个 zone 和自己比** |
| 三 | A 之前没有等 | **A 读的时候，这台手机动不动** |

三条的**共同点**不是"比较写错了"，而是：**这个设计从来没有为"手机在动"设过一道闸门**。
它防的是"漂移正好在 B 里冲高、到 C 消失"（docs 166 命名的盲区）；
它**没有**防的是"整趟都在动"，因为那被当成了一件**不会发生**的事——
而真机上它**每一次都可能发生**，这一次就发生了。

## 8. 修法：两条 hold，一条判据（`max_dev`），以及一个新的出口

改了三处，**它们是一条**：

**（一）比较换成 `max_dev`。** 它算的是**每一个** tsens zone 与它**自己**在窗口 A 的读数的差，
取**绝对值**最大的那一个，并把**符号**和 **zone 名**一起印出来：

```
   IT CAME BACK: every tsens zone is within 0.5 C of its own window A reading after 1s
   -- the largest difference was 0.0 C (0.0 C, on thermal_zone4 (tsens_tz_sensor3)).
```

"逐 zone"和"绝对值"是**同一件事的两半**：前者保证减号两边是同一个东西，后者保证"回来"两个方向都算。
而**符号被印出来**，是因为这一趟教的正是"5.0 °C"和"5.0 °C 往下"是两条完全不同的读数。

**（二）C 之前那个等待用它**（双向、逐 zone）。不回来时的判词 `no-return` 现在会说**方向**：

```
   IT DID NOT COME BACK within 4s: the largest difference from window A is 5.0
   BELOW window A's reading of the SAME zone (-5.0 C, on thermal_zone3 (tsens_tz_sensor2)).
```

**（三）A 之前加一条 pre-hold**（`--settle-start`，默认 300 s，`--settle-start 0` 关掉）。
两次相隔 `--poll` 的读数必须在**每一个** tsens zone 上一致到 `--margin` 以内，窗口 A 才被读：

```
== the pre-hold -- is this phone holding still, before a window is read at all?
   IT IS HOLDING STILL: after 3s, the largest change on any tsens zone in the last 1s
   was 0.0 C (signed 0.0 C, on thermal_zone1 (tsens_tz_sensor0)). Window A
   below is a STATE, not a point on a curve -- which is what makes B and C comparable to it.
```

一直不停就是**判词 `no-plateau`（退出 1）**，而它的位置很要紧：**它在窗口 A 之前、也在干预之前**，
所以**这是这个脚本唯一一个什么都不写的出口**（只有那次"同值写回"的证明写过，写的是核本来就持有的值）。
它印的是**它测到的那个移动**（"the largest change it still saw was 2.0 C"），
因为那是**下一次运行要跨过的东西**，而它和"governor 值多少"没有关系。

**这一趟如果用的是改完的仪器**，它会在 pre-hold 里等这台手机停下来（这一趟在 C 的时候读到 41.9，
说明它确实停得下来），然后 A / B / C 才都是状态。**判词会是哪一种，这一页不知道**——
这正是下一次上设备要去取的。

### 8.1 离线怎么被证明的：212 条检查，4 个新场景，3 个新变异

| 场景 | 造出来的手机 | 断言的是 |
|---|---|---|
| `plateau` | 每采样升 2 °C，到第 2 个采样停住 | pre-hold 等到它停（`after 3s`），然后 A/B/C 照常跑完并给出判词 |
| `no-plateau` | 一直升 2 °C，永不停 | 判词 `no-plateau`、**没有干预**、整棵树逐字节未变、仪器只被调了 4 次（全是 pre-hold 采样） |
| `below` | 撤销之后**比 A 低 5 °C** 且不再回来（**第二次真机运行的那台手机**） | 判词 `no-return`，而且印的是 **BELOW** |
| `zonewise` | 一条**不是最热**的 zone 回来时差 3 °C，别的 zone 精确回来 | 判词 `no-return`，点名的 zone 就是那条**不最热**的 |

| 变异 | 把什么放回去 | 由哪个场景驱动 |
|---|---|---|
| m11 | 去掉绝对值那一行（`if (d < 0) d = -d`） | `below`：手机低 5 °C 也被读成"回来"，然后**印出控制窗口自己的 −5.0 °C 当价钱** |
| m12 | 改成"取采样里最热那条 zone 的差" | `zonewise`：最热那条没动，于是"回来"了，跑到 C 去印一个判词 |
| m13 | 忽略 pre-hold 的答案（`if true`） | `no-plateau`：**干预照做**——这个变异的代价不是一个数字，是**对一台量不了的手机动了手** |

另外三条**静态**断言钉在源头（注释剥掉之后）：绝对值那一行**在**、等待用 `max_dev` 判定、
pre-hold 用同一个判据、`SETTLE_START=300`（默认**开**）。

## 9. 写这一轮时找出的第四个：fixture 的 zone 编号**撞了车**

它不是被断言抓到的，是**被一个变异的判词和预测对不上**抓到的：m12 在 `zonewise` 上**应该**印
`CONTAMINATED`（控制窗口那条走掉的 zone 会带 3.0 °C 进 C-A），**实际**印的是 `COST-MEASURED`
（C-A 最大值 0.0）。追这个 0.0 追到了 fixture：

stub 从 `thermal_zone0` 开始给 tsens zone 编号，而**真机上 `thermal_zone0` 是 `bms`**
（第二次真机运行自己的表就是这么写的：`thermal_zone0 bms`，tsens 从 `thermal_zone1` 起）。
于是 stub 把 **`thermal_zone0` 印了两遍**，而**每一个按 zone 名做键的读者都留下了最后那一行**——
delta 表就是那样的读者。所以：

* 那条**真正在动的 zone**（tsens 的 0 号）**在印出来的表里被 `bms` 那行顶掉了**——读者看不到证据；
* 判决里那个"控制窗口的最大升温"也**丢掉了那个 zone**，于是 3.0 变成了 0.0。

这一类形状这个仓库记过很多次（**一个 fixture 递出答案，于是被测的东西根本没跑**），
这一次的形态更细：**fixture 印了一个和真机不同的名字，于是被测的那条 zone 被另一条同名行盖掉了**。
改法是把编号改成真机的（tsens 从 `thermal_zone1` 起），受影响的五条断言跟着改。

**值得记的是它的可见性**：这个 fixture 从写出来的第一天就带着它，
而它**躲过了 161 条检查**——因为在此之前**没有任何一个场景依赖 tsens 的 0 号 zone**。
一个只被"这一次恰好用到了它"暴露的 fixture 缺陷，说明那些检查**没有一条问过"这张表和它说的是不是一回事"**。

## 10. 这一页**没有**成立的东西

* **②的价钱还是没有。**这一趟**印**了一个 3.5 °C，而这一页说它不是价钱——所以到这一页为止，
  第二个成因的价钱仍然**一次都没有量到**。它也没有被反驳。
* **修完之后没有上设备。**212 条检查全是对着假设备跑的。pre-hold 在**真**手机上要等多久、
  `no-plateau` 在真机上可不可达，**都不知道**。
* **热时间常数还是没有。**这一趟给了它一个**下界**（10 秒就"回来"了，因为它在往下走），
  但那个数不是时间常数，是**漂移速率**。
* **一趟、一个负载、一个环境。**环境温度、充电状态、屏上有什么**都不受控**，
  和 docs 167 的 5.5 °C 带的那组限定是同一条。而且这一趟比上一趟**更糟**：
  它开始的时候手机是热的（A 49.6），这是它整趟往下掉的原因。
* **控制窗口还有一个没修的洞**：等待证明的是**窗口 C 开始时**的状态，
  而 C 自己要跑 45 秒——**那 45 秒里手机可以再动**。这一趟没有暴露它，但它在那儿。
* **设备时钟是错的**（读 1970-02-13）：仪器印的每一个时间戳都是错的，真实日期在存档表头里。
  这一条不影响温度读数。
* **跨重启的持久性仍然没量过**（docs 168 就留着这一格）：这一趟没有重启。
