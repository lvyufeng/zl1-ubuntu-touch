# Status — 2026-09-17

Where the zl1 Ubuntu Touch port actually stands, what is blocked, and what one
button press unblocks.

## Live state

| | |
| --- | --- |
| Repo | clean, everything pushed to `master` (`4fe09c7` and earlier) |
| Device `33e80afe` | powered on, sitting in a **stalled Ubuntu Touch boot** |
| Device USB | RNDIS gadget only — the host sees an interface with `carrier=1` and receives nothing |
| Host-side recovery | **exhausted** — see `22-stage2-coldboot-results.md` §5.2d |
| Waiting job | `twrp-one-shot-setup.sh 900 28800`, running, 8-hour window |

## The one thing that is blocked

Reaching the device again. It exposes RNDIS and **not adb**, its HTTP status page
is read-only, and the stall is a dead transmit path, so nothing can be read out
of it and nothing can be commanded through it.

Five host-side levers were tried, all ineffective:

| Attempt | Result |
| --- | --- |
| `modprobe -r rndis_host` then reload | usb0 re-registers, link still dead |
| `/sys/bus/usb/devices/3-3/{unbind,bind}` | same |
| `authorized` 0 → 1 | same (the device's host MAC changed, so its gadget did re-bind) |
| `USBDEVFS_RESET` — a real bus reset | same, and dmesg confirms the device re-enumerated |
| runtime PM suspend/resume | not possible: `runtime_status` stays `active`, usbnet holds the reference |

That the gadget re-enumerates and the link stays dead is itself informative: the
fault is not host-side state, and it is not anything a re-enumeration clears. It
is state on the `net_device`, which `u_ether` keeps across connect/disconnect —
consistent with the confirmed code fact behind
[`23-uether-tx-wakeup-patch.md`](23-uether-tx-wakeup-patch.md).

**One physical action fixes it:** power off, then hold **Volume Up + Power** for TWRP.

## What that press sets off

`twrp-one-shot-setup.sh` is already waiting. On reaching TWRP it will, without
further input:

1. back up `misc` (the 2026-06-07 set has no image of it)
2. install the netwatch watchdog — it records the RNDIS gadget's own counters
   (`tx_pkts_rcvd` / `tx_qlen` / `tx_throttle` from u_ether's debugfs), the interface
   counters and routing state; takes a one-shot hardware snapshot for the later
   display/touch work; and re-asserts the gadget in two escalating stages when it
   detects a stall
3. fix SSH public-key login by pointing `AuthorizedKeysFile` at `/etc/ssh/authorized_keys.d/%u`
4. write the marker that makes the device ask the bootloader for recovery after 15
   minutes, so its log can be read without touching it
5. reboot into Ubuntu Touch

After that the loop closes: UT boots and records, heals itself if the link stalls,
and returns itself to TWRP. `netwatch-cycle-supervisor.sh` then repeats that
unattended, which is how "does the patch help?" gets answered — it is a question
about a rate (~1 boot in 4 stalls), not about one boot.

## The immediate next steps, in order

1. **Human:** Volume Up + Power → TWRP. Everything below follows automatically.
2. Validate the watchdog on the configuration already known to work: the first
   cycles deliberately do **not** change the boot image, so the watchdog is tested
   on its own before anything else moves.
3. Read `docs/ubuntu-touch/stage2-coldboot-trials.md` — three consecutive
   matching rows is Stage 2.4, and until now that criterion had never had a
   record behind it.
4. Run Stage 2.5's drill (`stage2-rollback-drill.sh`): flash a documented-bad
   image, confirm it fails, restore the stock `boot.img`, confirm the device
   boots. That is what turns "there is a verified rollback" from a statement
   about a file into a statement about the device.
5. Then the A/B that matters: `halium-boot-zl1-v63-uether-txwakeup.img` versus
   v63, same initramfs, kernel the only difference. Stall counts on both sides.
6. `fix-ssh-authorized-keys.sh` has not been confirmed on hardware yet — the
   next boot is its test. If it works, every later session gets a shell over the
   network instead of a status page.
7. If the patch does not remove the stall, the next escalation is on the device
   side, where the host cannot reach: the watchdog's stage-B heal already
   rebinds the function, which is strictly stronger than anything tried from
   here.

## What is genuinely done

- **Stage 0** — `userdata` (26.1 GB) and `cache` backed up and byte-verified
  against the device; 31 existing backups re-verified against the live partition
  table; the boot partition confirmed byte-identical to the 2026-06-07 image.
  See [`18-stage0-backup-record-2026-09-16.md`](18-stage0-backup-record-2026-09-16.md).
- **Phase 1** — the build is byte-for-byte reproducible, and the reason the
  original target hash was unreachable turned out to be a stale initramfs
  timestamp in the *reference* image, not a build fault.
  See [`19-phase1-reproducible-build.md`](19-phase1-reproducible-build.md).
- **Stage 2.2/2.3** — `fastboot flash boot` plus a cold boot reaches Ubuntu Touch:
  systemd as PID 1, `rndis0` up, and with `/data/system.img` restored the Android
  container runs with its full HAL set. See
  [`22-stage2-coldboot-results.md`](22-stage2-coldboot-results.md).
- **The working image is no longer only a binary** — v63 rebuilds from tracked
  source and every rebuild is content-verified against it, deterministically.
  See [`24-reproducible-working-image.md`](24-reproducible-working-image.md).

## What is not done

- Stage 2.4 (three consecutive cold boots) and 2.5 (rollback drill) — scripts are
  written and waiting; neither has been run, so neither is claimed.
- The transmit stall — mitigated and instrumented, not fixed. Root cause still a
  hypothesis with supporting code evidence, not a proof.
- SSH over the network — fixed in principle, unverified on hardware.
- Phase 5 display and touch — hardware snapshot collection is in place; neither
  has been assessed.
