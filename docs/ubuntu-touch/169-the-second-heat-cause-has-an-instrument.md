## 1. 一句话结论

| 这一页要量什么？ | **第二个散热成因值多少度**：镜像把四个核**全钉在 `performance`**，修法（`install-cpufreq-governor.sh`，docs 164）把 `interactive` 写进去、并用一个每开机重设的 unit 守住它。 |
| 为什么它一次都没单独量过？ | 因为 docs 167 那一趟**把①和②当背景**，只量了③。原文在它自己的第 5 节：三个成因都装着，那一趟量的是第三个。所以"第二个成因值多少"这个问题，**修法装上之后一次都没有被问过**。 |
| 能直接 A/B 吗？ | **不能**，理由和 docs 166 一模一样，而且是量出来的：这台机器**在没有任何改动的情况下会自己变热**（相隔约一小时的两个只读窗口，最热 tsens zone 45.6 → 50.9 °C）。两个窗口量到的差值里，governor 的贡献和"手机在变热"分不开。 |

## 2. 为什么"②值多少度"这个问题到今天才被问

三个成因装上之后的稳态读数（docs 164）说的是"三个修都**开着**"，
它**一个字也没说它们买到了什么**。docs 166 把这件事变成了一个仪器，docs 167 把它跑了一次：
**挡住睡眠阶梯，最热 tsens zone 高 5.5 °C**。

但那一趟的设计里有②：三个窗口全程四个核都已经是 `interactive`（修法装着的状态），
所以②在那一趟里既不是变量、也不是被定价的对象，它是**背景**。
docs 167 自己没有含糊这一点，它在第 5 节写明了"②的效果一次都没单独量过"。

于是这个成因的处境和③在 docs 164 时的处境一样：**修装上了，价钱不知道**。
而"不知道价钱"在这里不是一个学术问题——三个修都装着、idle 43–51 °C 的稳态读数是**修复之后**的样子，
它是"发热被解决了吗"这个问题的**分子**，而它的分母（每个修各值多少）里少了一块。

## 3. 旋钮是四个文件：为什么这一条改变了整个仪器的形状

ladder 仪器（docs 166）和这一台是同一个三窗口设计，同一套判词词汇，同样的 0.2 °C 分辨率，
**连取最大值的规则都一样**（只取 `tsens_tz_sensor*`：电池和 pm8994 是跟着充电器走的，
那里的差值是**供电**的差值）。差别只在旋钮，而旋钮的形状决定了三件事：

**（一）每写一个核都要读回，而且要一起读回。**
`scaling_governor` 是一个每核一份的文件。内核**不接受**的 governor 名不会报错，它只是**不改变文件**——
所以一个"写进去了"的假设会把两个完全相同的状态当成 A 和 B，然后报出 `no-detectable-cost`，
而那正是这个实验**最像结论**的一句错话。四次写里有一次没落地，报出来的是**四分之一的价钱**，
比真实值小，方向还像真的。所以 `write_gov` 写完全部核之后**逐核读回**，只有全部等于写入值才返回 0，
`gov_state` 给整台机器一个词：四个核一致的那个值、`mixed`、或者 `none`。

**（二）没有字母表，也没有 `tr` stub，而这是一个属性、不是一个省略。**
ladder 的参数是 **bool 模块参数**：文件里存 `0`，读者把它**渲染**成 `N`，
所以那个 harness 必须有一个 `tr` stub 把模块的类型带进去（docs 163），
一个纯文本 fixture 表达不了这件事。**governor 的名字是原样存、原样读回来的**——
所以在这里，一个纯文本文件**就是**那台设备，而且 harness 里那条"写一个值再读回"的断言
是在断言一件 fixture 能诚实做到的事。这一条是**在设备上核对过**的（第 6 节）。

**（三）"各个核不一致"必须是一个能够到达的状态。**
如果 A 窗口里四个核本来就不同意，那这个实验没有 A 可言——它连"装机状态"是什么都答不出来。
所以拒绝 D 先查 `mixed`，再查"它们读的不是 `interactive`"，两个是不同的拒绝理由。

## 4. 写 harness 时找出来的缺陷：一个在仪器里，四个在 harness 里

**仪器里这一个是真的会印出错误读数的。** 核心的名字要从它的路径里取出来，
而 `/sys/devices/system/cpu/cpu0/cpufreq/scaling_governor` 这条路径里 `/cpu` 出现**两次**
（`system/cpu/` 和 `cpu0/`），再加上 `/cpufreq` 里的第三次。两个"显然"的写法**都是错的**，
而两个都在这里被量过：`${p#*/cpu}` 会切到**第一个** `/cpu` 之前，留下 `/cpu0/cpufreq/...`；
`${p##*/cpu}` 会切到**最后一个**之前，留下 `req/scaling_governor`。
第一版印出来的是 `cpu=` 后面**一个空名字**——在一个**存在的全部意义就是说出是哪个核**的诊断里。
修法是先剥掉已知后缀、再取最后一段（`cpu_name()`），这样没有任何歧义。

**harness 里四个，其中三个是这个仓库已经记过的形状又来了：**

1. **fixture 写的是 `interactive\n`，而仪器写的是没有换行的 `interactive`。**
   这条断言一开始红，报的是"the run left the tree changed"。fixture 要模拟的是**往返**，不是那个文件。
2. **mutation 里用了 `\|`，而 GNU sed 的 BRE 里 `\|` 是"或"。** 于是模式匹配的是**一段跨度**而不是一行，
   mutant 根本没解析成功，harness 报的是"the mutant does not parse"——**不是**它被造出来要暴露的那个缺陷。
   在这台机器上，"我的 mutant 是坏的"和"我的 mutant 证明了缺陷"看起来完全一样。
3. **拒绝 C 的 mutation 把 `scaling_available_governors` 里两个 governor 都删了**，
   而不是删掉在被测的那一个。于是 mutant 照样拒绝，只是**叫错了名字**——
   一个 mutant 必须把**另一个** governor 留着，否则它测的是"这个文件为空"而不是"这个值不被提供"。
   （这就是 docs 166 第 7 节那个"永远不可能报警的检查"的同一个形状，只是换了一层。）
4. **一个 scenario 删掉了整个 cpu 树，把它后面的十一个 scenario 全弄红了。**
   所以假设备现在由一个函数（`gc_mk()`）建，每一个 scenario 都先调它——
   这一条写在文件里，因为**这个文件的第一版就是这个 bug**。

另外有一条断言**本身就是错的**：同一个值的写入证明，一开始拿错的字符串去比。
它现在是 `wrote 'interactive' back to all 4 core(s) and read 'interactive.'`。

harness 的 8 个 mutant 里，**7 个要跑起来并改变**上面某一条断言的观察结果；其中三个值得点名，
因为它们是"一次不可能失败的检查"的三种形态：
**m1** 把控制窗口关掉，于是漂移被当成 governor 的价钱印出来（`COST-MEASURED`，而正确的判词是 `contaminated`）；
**m5** 拿掉 offer 检查，但**必须由一个"内核不提供这个值"的 scenario 来驱动**——
其他 scenario 的核**都**提供 `performance`，所以一个永远不可能报警的检查从通过的那一侧根本看不见；
**m7** 拿掉 panic 门，同样必须由一个 `download_mode=1` 的 scenario 驱动。
m0 是**只看不跑**的：它在 `set -u` 后面加第五个重定向目标，harness 必须在**没运行它**的情况下看见它。

harness 还有一节（第 9 节）是**引用自己**的：它去读 `host/zl1-health-check.sh`，
断言那条引用里的条数等于**这一趟实际跑出来的条数**。所以"这一页的仪器在健康检查里被引用了"
这句话是**被引用者自己检查的**——它现在写的是 **116**。

**这一轮还顺手证明了那条防漂移的链子是活的，而且它是自己响的。** 往树里放两个新脚本，
`zl1-cli-usage-selftest.sh` 的覆盖面就从 90 个脚本变成 92 个（页面上按路径写出来的从 85 变 87，
其中 harness 从 38 变 39），于是它自己的条数从 **222 变成 226**——
而它的第 5 节当场红了，因为健康检查里那条引用还写着 222。**这条检查不是为了这件事写的，
但它对这件事生效了**：不用记住"加了脚本要改数字"，数字自己会喊。
两个页面（健康检查、`scripts/README.md`）上的每个条数都在同一条链上：第 4f 节把 README 的每一行
和健康检查里**被验证过的那条引用**逐行配对，所以三处（harness 自己、健康检查、README）是一致的，
**不是靠人肉同步的**。

## 5. 判词、退出码，与"它写完之后设备在哪里"

判词三选一，阈值**印在判词旁边**（一个看不见的阈值就是一个没法争论的阈值）：

| 判词 | 含义 | 退出码 |
|---|---|---|
| `cost-measured` | B 比 A 高过分辨率，**而且 C 落了回来** | 0 |
| `no-detectable-cost` | B 没比 A 高过分辨率——**这个脚本反对它围绕的那个修** | 0 |
| `contaminated` | 升温持续到了 C——**这是在说这一趟，不是在说手机** | 1 |

一个**没落地的干预**、或者一个**没守住的撤销**，**根本不是判词**：它退出 4 并把状态印出来，
因为那下面每一个数字都是两个相同状态的比较。

它写的东西：**四个 governor 文件，别的什么都没有**。没有分区、没有块设备、没有模块参数、
不重启任何服务、不重启机器。它写回去的值是**修法自己的值**（`interactive`），
所以即使 trap 全都没起作用，它也停在被找到时的状态上——而且退一步说，
开机时 `zl1-cpufreq-governor` 那个 unit 下一次开机还会再写一遍 `interactive`。
这个"最多只能跨一次开机"的性质和 ladder 仪器是同一条推理，写在这里是因为它是**撤销的最后一层**，
而最后一层不应该是 trap。

## 7. 这一页**没有**成立的东西

* **它没有在设备上跑过。** 判词、退出码、trap、读回、四个拒绝，**全部**是在一个假设备上验证的。
  设备上的读数只有第 6 节那两条只读的。**"②值多少度"这个问题现在仍然没有答案**——
  这一轮买到的是一条**能回答它的命令**，以及"这条命令在被信任之前必须先跑通它的 harness"。
* **一趟、一个负载。** 即使跑起来，它给的也是一个负载下的一个数：环境温度、充电状态、屏幕上有什么
  **都不受控**。docs 167 的 5.5 °C 就是带着这组限定被记下来的，这一台如果跑出数来也要照样记。
* **它不量"哪个核在烧"。** 它量的是 governor 状态下温度的最大值差。哪个进程在烧是 `zl1-thermal.sh` 的事。
* **它不量笔记本。** 它不区分"LITTLE 集群动"和"BIG 集群动"以外的任何东西，也不读
  `scaling_cur_freq`——所以一个"governor 换了但频率没变"的设备会让它报出 `no-detectable-cost`。
  那不是错的判词（那个成因确实没买到温度），但它**不是**一个关于 governor 名字的读数；
  要分开这两者，得先读 `scaling_cur_freq`，那是下一个仪器的事。

## 8. 阶段位置

散热那三条里，①（debug keeper）和③（睡眠阶梯）都有仪器、都有读数；**②现在有仪器了，还没有读数**。
三件这件事带来的：

| | 之前 | 现在 |
|---|---|---|
| ②的价钱 | "一次都没单独量过"（docs 167 §5） | **有一条能问的命令，离线全绿（116 条）** |
| 旋钮的形状 | 一个 bool 参数、一个字母表 | **四个文件**：每核写、每核读回、要求一致 |
| 读错了会怎样 | —— | `no-detectable-cost`：**最像结论的那句错话**，所以 offer 检查和 `mixed` 是两道拒绝 |

下一个阶段是**把这条命令在设备上跑一次**（它需要先推 `/tmp/zl1-thermal.sh`，
拒绝 B 就是为这件事存在的），拿到②的价钱或者 `no-detectable-cost`——
然后散热这一栏才有资格说"三个成因各自值多少"。硬件清单上还没驱动起来的那几项（相机 app 上没上屏、
GPS 一次定位都没有、指纹的驱动编进了镜像但没刷）**这一轮一个都没有碰**。
