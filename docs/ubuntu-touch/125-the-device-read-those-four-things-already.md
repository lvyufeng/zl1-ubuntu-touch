## 2. 四条，逐条给出处在哪儿

读数全部来自这两份归档（它们是 doc 107 那条命令在 2026-09-23 和 2026-09-24 两次真机运行留下的）：

| doc 86 §5 说"一次都没出现过"的 | 真机上的读数 | 出处 |
|---|---|---|
| `/sys/module/msm_poweroff/parameters/download_mode` **是不是这个路径** | `/sys/module/msm_poweroff/parameters/download_mode = 1` | `tmp-post-recovery-20260923T145530Z/01-edl-postmortem.txt:14`、`tmp-post-recovery-20260924T013059Z/01-edl-postmortem.txt:13` |
| `/sys/kernel/dload/` **存不存在** | ` /sys/kernel/dload: emmc_dload ` 且 `emmc_dload = 0`（归档自己注明：这是 dload 的**类型**，不是那个开关） | 同上两份，各自 §1 |
| `/sys/fs/pstore` 复位后**是不是真有东西** | **目录存在、里面是空的**（"EMPTY. No oops on record."） | 同上两份，各自 §2 |
| `/userdata/zl1-kmsg/keep/` 里**是不是真躺着那个死掉的 boot** | 有 4 个 `keep/boot-<boot_id>/`，每个 9 个文件；其中 `boot-0488bd3c-…` 是**上一个** boot，**带死亡特征和 Call trace** | `tmp-post-recovery-20260924T013059Z/01-edl-postmortem.txt` §3 |

**第三行必须拆成两半说，否则就是这一轮自己犯要修的那个错**：

* **被回答了的是**：那个**目录存在，而且可读**——postmortem 的源码是
  `if [ ! -d /sys/fs/pstore ]` → "does not exist"，**否则**才可能是 "EMPTY"（
  `scripts/device/zl1-edl-postmortem.sh:168`），归档打的是 EMPTY，**不是**"不存在"。
  所以"路径在不在"和"读它会不会失败"都不是猜的了。
* **没有被回答的是**：**pstore 到底能不能活过一次复位**。空的 pstore **什么都不能证明**——
  它既符合"上一次没 panic"，也符合"ramoops 区没活过复位"。归档自己把这句话印在同一段里，这一页照抄。

**第四条还有一层**：那两份归档不只证明了路径，还**给了 2026-09-23 那次 EDL 第一个归因**——
postmortem 的判语是 FOUND，证据在**第二个见证**（kmsg 归档）里，不是 pstore。
doc 86 §5 最后那句"不证明 2026-09-23 那次就是 panic"里的"要等设备回来"**已经发生过**。

## 3. 一处推理被写成了读数：doc 122 §72

`122` 里那张门表的第一行，括号里的理由是：

> `（/sys/module/*/parameters/download_mode`，**按 glob 找，不按名字**，因为 docs 86 记过电源驱动的名字和字符串搜索的猜测不一致）

**86 没有这么记。**86 §5 的原文是"`msm-poweroff.o` → 模块名**应是** `msm_poweroff`，
**没在真机上确认过**"——它说的是**没确认**，不是**不一致**。而设备的读数是 `msm_poweroff`：
**猜测和读数一致。**

所以这段不是"引错了一句话"，而是这一族里最熟的那一种：**一个推理被写下来之后，读起来和一个读数一模一样**，
下一个人（包括我自己）就会拿它当理由用。glob 仍然是对的——但它的诚实理由是**鲁棒**（换内核/换名字都还能找到），
不是"名字和猜测不一样"。`122` 已改成这个说法，并且指到这一页。

## 4. 一个真的代码后果：读一个，和写全部

`read_download_mode()` 原来读**第一个**匹配就 `exit 0`。写这个旋钮的那个 unit 不是这么做的：

```sh
# install-no-edl-on-panic.sh 的 applier，落到设备上的那份
for p in /sys/module/*/parameters/download_mode; do
    ...
    echo 0 > "$p"
    after=$(cat "$p")
    [ "$after" = 0 ] || { echo "…did NOT clear…"; ok=0; }     # ← 任何一个没清掉，unit 自己判失败
done
```

同一个 glob，**写的一方读全部、任何一个没清掉就自报没武装**；**读的一方只看第一个**。
在设备今天这个形状下（**只有一个**参数，见 §2）两者不会分歧——**但这不是"读得对"，
这是"今天恰好只有一个"**。一旦有两个，runbook 可能打出 **"A is MET"**，而那个负责武装 A 的 unit
自己在 `systemctl --failed` 里说**没武装**——两条关于同一个旋钮的结论互相矛盾，
而**没有任何东西会告诉你哪一条是假的**。

现在 `read_download_mode()` 读**每一个**匹配，输出一个**自己形状的 token**：

```
all=0 (N parameter(s))                 全部读 0   -> A 满足
ARMED <path>=<value>[ <path>=<value>]  至少一个不是 -> A 不满足，并点名是哪一个
NOT-FOUND                              驱动根本没暴露这个参数
```

判语也从"值在哪个位置"改成"**是不是这个 token**"。这不只是修 bug：原来那个 `case` 靠
**位置**（`*=0` 匹配 `<path>=<value>` 的末尾）来判读，而这一页前面刚刚说了，
**位置这种东西在这个项目里已经错过两次**（先是 `0*`，再是 `*=0`）。token 把"形状对不对"
变成一条能核对的判断，而不是一个隐含假设。

## 5. 连带修掉的：harness 的 fixture 曾经用一个**编造的名字**

runbook 的 harness 里，`download_mode` 那个 fixture 的模块目录名原来是 `msmpoweroff_msm`——**编的**。
它的注释给了理由："doc 86 记过真名不是字符串搜索猜的那个，用期望的名字会让 glob 坏掉也照样通过"。
这个担心是对的，**答案用错了**：一个**编造形状**的 fixture 证明不了"读得对**设备那个形状**"能工作，
而 doc 86 那句"真机路径没出现过"在归档被写下的那一刻就**不成立了**。这正是
"**fixture 必须有真实的形状**"这条老账。

现在 fixture 有**两个**模块目录：

* **主参数**用**设备的真名** `msm_poweroff`（§2 的读数），所以每个不问"两个"的场景都在真实形状上跑；
* **诱饵**叫 `qcom_poweroff`，**故意排在主参数之后**（glob 按字典序展开），所以"只读第一个"
  和"读全部"**必须给出不同答案**。

**而诱饵的第一个名字证明了这条注释的必要性**：最初用 `msm_mpoweroff`，它**排在 `msm_poweroff` 之前**，
于是两种实现读的是同一个参数、**给出的答案一致**——变异跑下来，那条为它写的断言**没红**。
**一个不能让两种行为分岔的 fixture，测的不是这两者**。换个名字之后，
变异"只读第一个匹配"从红 0 条变成**红 5 条**，其中就包括为它写的那一条。

## 6. 这一篇**不**证明什么

* **不证明设备上现在是这样。**这一页的一切都来自**别的 boot 留下的归档**，本轮没有碰设备（仍在 EDL，
  `05c6:9008`，`Bus 003 Device 020`，无序列号）。
* **不证明 `download_mode=0` 在真机上真的生效。**那个 unit **从来没装过**——所以"读回 0 就说明
  一次 panic 会正常重启"仍然是**没验过的**（doc 86 §4 的老账，这一页没有消掉它）。
* **不证明 pstore 活得过复位。**见 §2 第三行：归档里它是**空的**，而空正是什么都不证明。
* **不证明"四个参数"存在。**设备读到的**只有一个**；§4 修的是**读法**，不是一期真实的多个参数。
* **不证明归档本身没被改过。**它们是 `tmp-*`（gitignored）里的文件，不是版本控制里的证据；
  能核对的是它们**内部一致**（同一次运行的 00–06 与 INDEX 对得上），不是它们没被编辑过。

## 7. 下一步

设备出来的那一条命令没有变，**读法变了**：

```
# 0. 物理长按 POWER 10–20 秒，等 RNDIS 和 ssh
scripts/host/zl1-one-boot-runbook.sh --status    # 只读，现在会告诉你它看了几个 download_mode 参数
scripts/host/zl1-one-boot-runbook.sh --yes
```

出来之后**第一个能填的老账**是 §6 里那条：`--install`（第 02 步）**会**写 0 并读回验证，
所以那一步跑完之后，"写 0 到底生不生效"就不再是没验过的了——**而那正是实验的门 A**。
